# ADR-0004: 守卫按「失败的含义」分硬/软两档（Two-tier guard verification）

- **Date**: 2026-09-30
- **Status**: Accepted
- **Deciders**: YV3507
- **Amended by**: [ADR-0006](./0006-comment-discipline-as-written-convention.md)（软档内的**文档类**守卫后续被撤除）

> 分档判据与两档清单的现状在 `docs/TEST-LAYOUT.md`；本文只记**为什么分档**。

## Context

本仓的验证面由大量独立守卫构成（`test/verify-*.mjs` 等），它们共用同一个出口：非零退出码。

分档之前的问题是：**所有判据共用同一种红**。于是一次**文档排版**改动与"发布面漏了一个文件"
会让**同一条命令**失败 —— 改一行的合规成本被最贵的那条判据决定。后果是：

- 贡献者倾向于**绕过整条链**，因为跑一次太贵；
- 真正危险的失败（用户会撞上的）被淹没在无关的红里；
- "让链变绿"的动机变成改判据，而不是改代码。

这个形态不是判据数量的问题，是**失败语义被压平**的问题。

## Decision

**按"失败的含义"把守卫分两档**，而不是按"判据重不重要"：

- **硬档**：失败意味着**用户会撞上** —— 真机行为、发布面、平台契约、打包面。
  跑在 `npm run verify` 与 CI 里，**挡 PR**。
- **软档**：失败意味着**仓库内务 / 账本自洽 / 一次性清理的验收判据**不准了 ——
  要人回来看，但不该拦住别人的改动。跑在 `npm run verify:docs`，**只出声、不挡人**。

配套决定：

- **D1 —— 分档只改"谁决定红绿"，判据本身一字不动**。降级的是**退出码**，不是判据。
- **D2 —— 软档照跑、照打印 `✓/✗`**，原退出码写在末尾的显式行上并写进环境变量，
  供 CI / 脚本读取。
- **D3 —— 跳过不得与通过同形**：确实跑不起来的前置条件（例如本环境起不了子进程、
  缺真浏览器）要么**红**，要么要求**显式声明跳过**并点名原因。静默跳过等于悄悄失去覆盖。
- **D4 —— 入口用子进程包装，不用 `node --import`**：因为包管理器会吞掉 `--import` 参数，
  降级会失效、链条当场断在第一条软档守卫上（这是实测到的，不是推测）。
- **D5 —— 新守卫按"失败时用户会不会看到错的行为"定位**；拿不准的**放软档**
  —— 硬档的门槛是"能说出用户侧后果"，说不出的先别挡人。

## Consequences

**收益**

- **合规成本与改动风险成正比**：改文档不再需要满足发布面的验收标准。
- 硬档恢复信噪比 —— 它红的时候，是真的有用户侧后果。
- 判据全部保留（D1），覆盖没有因为分档而丢失。

**代价（我们放弃了什么）**

- **软档会被长期忽略**：只出声的东西没人看，这是分档的固有代价。本仓后续的应对是
  **直接撤除文档类软档守卫**（见 ADR-0006），而不是靠 "记得看"。
- **多一层包装**（D4）让"某条守卫到底绿不绿"需要读原退出码，而不是看命令成败。
- **分档判断本身需要人来拍**，且拍错的成本不对称：把该硬的放软，等于失去保护。

## 重新考虑的触发线

- 软档长期全绿但仓库内务实际在腐化 ⇒ 说明软档既没挡住问题、也没起到提示作用，
  应**撤除**而不是"再强调一次要看"。
- 硬档开始出现"说不清用户侧后果"的判据 ⇒ 说明门槛松了，应把它移回软档或撤除。
- 上游 CI 支持**按失败类别聚合**时，可用更细的表达替代这条两档近似。
