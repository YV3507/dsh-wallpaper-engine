# 问题留档：JPEG 回退路径返回透明黑 → 背景整层不可见（已修复）

状态：**已修复** ｜ 修复提交：`fix(renderer): JPEG 回退路径返回透明黑导致背景整层不可见`

## 症状

壁纸 `2934788040`「花（静态）」(`type: scene`，本项目按静态帧渲染) 背景**本应是黑色**，
实际呈现**亮灰** `(179,179,179)`。

## 根因

该场景 `scene.json` 声明 `general.clearenabled = true`、`general.clearcolor = "0.70000 0.70000 0.70000"`
⇒ 清屏色 `(179,179,179)`。场景里有一个**全幅背景对象**（4608×2592，正好等于 `general.orthogonalprojection`）
本应把它盖住，但该对象的纹理是 **JPEG**：

- `lib/we-renderer/jpeg.js` 的两条**回退**路径（catch 分支、周期性熵早退）直接
  `new Uint8Array(w*h*4)` ⇒ **alpha 全 0**（而旁边注释写的是"返回纯黑"）；
- `blitScaled` 跳过 `a <= 0` ⇒ **背景对象整层不参与绘制**；
- 于是露出本该被盖住的 clearcolor 灰。

正常解码路径其实**本来就设了 `alpha = 255`**（`:454`），两条回退与之不一致 —— 这是纯粹的疏漏。

## 决定性证据（为什么"以前是黑的"是意外）

| 实验 | 结果 |
|---|---|
| `DSH_DIAG_SKIP=9d70e8e0`（隐藏该背景对象） | **与不跳帧逐字节相同** ⇒ 它本来就画了 0 像素 |
| `DSH_DIAG_SKIP="图层 2"`（隐藏花朵） | 整帧**恰好 100%** `(179,179,179,255)` ⇒ **没有对象在画这块灰**，它就是 clear 填充 |
| 用 jpeg-js 独立解码该纹理 | 4608×2592 均值 `(0,0,0)`、alpha 255、100% **不透明黑** |
| 作者自带 `preview.jpg` | 边缘均值 `rgb(18.0,19.9,26.0)`、四角近黑 ⇒ 作者意图就是黑底 |
| 只在临时副本里把回退 alpha 改成 255 | 角点 `(0,0,0,255)`、77.8% 纯黑，**花朵像素不变**，均值回到修复前水平 |

⇒ 之前"看着是黑的"，是因为那块区域**透明**、叠在黑色桌面上；一旦合成到不透明背景（或本次
`clear()` 修复让 clearcolor 生效）就会露出灰。**修 alpha 才是正解**。

## 修复

| 位置 | 改动 |
|---|---|
| `lib/we-renderer/jpeg.js:186-190` | 新增 `opaqueBlackRgba(w,h)`：分配后按 alpha 步长填 255，RGB 保持 0（无额外拷贝） |
| `lib/we-renderer/jpeg.js:201` | catch 回退改用 `opaqueBlackRgba` |
| `lib/we-renderer/jpeg.js:402` | 周期性熵早退同样改用 |
| 正常路径 `:454` | 未改动 |

## 相关决定与残留

- **上一处 `clear()` 修复保留**（不回退）：`core.js:674` 本就用 `clearenabled !== false` 守卫，
  且 `scene-render-worker.mjs:78-88` 的空帧门禁**本来就假定 clearcolor 已生效**；
  回退它反而破坏自身一致性。两张已核对的壁纸（`3640755971` 深灰 `(78,78,78)`、`3641860575` 逐字节不变）都支持保留。
- 未验证：**未全量扫描**工坊中"会走 JPEG 回退"的壁纸（本次只查了 3 张指定 id）。现行为与
  libjpeg/Windows 一致（返回不透明黑）；若存在"损坏 JPEG 且该对象本就期望不可见"的壁纸，行为会由透明变黑。
- 旁注（未处理）：`copybackground` 在 `lib/we-renderer` 内**从未被读取**（潜在未实现特性）。
