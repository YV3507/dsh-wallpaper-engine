## 1. 决策（先结论）

**不做立刻的结构性大重构**：先做一轮「减重 + 加固」，再按已验证的接缝分批抽取。

三条依据：① 病灶是**体量集中 + 边界缺失**（两个门面文件仍占手写代码约 27%），不是逻辑纠缠；② 守卫是唯一的安全网，
大重写会先拆掉它，而缺陷率与回滚史说明"一次改对"不成立；③ 当前最高风险曾是**零 CI**，已先补掉。

**顺序**：`P0 加固 ✅` → `P1 单一真源 + 零耦合抽取 ✅` → `P2 按接缝分批`（P2-9/P2-10 ✅；P2-11 的余族见 §5 状态列）→ `P2-12 静态帧线整体移除 ✅`。
**并行功能轨道**：`F 字体系统大改`（F0–F3 ✅）—— 它的数据模型建立在 P1-5 之上，故排在其后。

### 3.5 E：`apply(ctx)` 拆分的必要性评估

> 复算：`node test/tools/analyze-host-apply.mjs`。
> **结论：不整体重写** —— 先做三条前置，之后**按路由族拆、一次一族**。触发条件见 §7 第 6、7 条。

**为什么不现在拆**：① 没有具体病痛指向它（对比 P2-9：那时有 26 处裸 `fetch` 的具体隐患）；② 代价是 **22 个共享可变闭包状态**

④ 没有"必须现在做"的外部压力。

**三条前置**（已全部就绪）：① 路由索引 `docs/ROUTE-INDEX.md` + `verify-route-index.mjs`；② 三条零覆盖路由补真实行为断言；

⚠️ 第 ③ 步顺带更正一个**误测**：早期把"到下一个同级声明的距离"当体量，量成 1,795 行；真值 **293 行 ≈ `apply` 的 15%** ⇒
`apply` 不是"几块大肉"，而是 **~30 个中等处理器 + 助手共享 24 个闭包状态** ⇒ **更支持按族拆**。

**每族的固定动作**：① 新建 `lib/routes/<族>.js`，导出 `register<族>Routes(webServer, c)`，族内共享的随族搬走；
② `apply` 里改成一次调用，**共享可变状态只以引用进 `c`，不做拷贝**；③ 重新生成 `docs/ROUTE-INDEX.md`；④ 该族的守卫必须先存在。
后续族：`inventory` → `upload` → `scene` → `media`；被多族复用的助手（`serveFile` / `handleSceneFiles`）留在 `apply` 里、以引用进各族 context。

## 6. 静态帧线移除后的形态（**已落地**；机制在代码里）

> 本节曾是"目标设计基线"（14 个小节的论证与取证）。P2-12 已按它执行完毕 ⇒ 此处只留**契约**与
> **仍在生效的裁定**。机制细节的权威来源是代码：`lib/routes/scene-frame.js` 的文件头（出图来源链
> 与档位值域）、`lib/index.js` 的 `sceneFrameCacheKey`（缓存键）、[`HOW-IT-WORKS.md`](../HOW-IT-WORKS.md)（用户可见行为）。

**出图来源（唯一权威顺序）**：① 实时渲染 iframe → ② 作者内嵌 MP4（`sceneVideo`）→ ③ **实时抓帧**
（`<key>_gpu.png`，live 页首帧确认后回填）→ ④ **自定义画面**（用户导入）→ ⑤ **空态**（404 + 可判定原因）。
**没有"替作者猜一张图"的来源**（静态帧提取 / 合成 / 找最大图片 / 工坊预览图都已删除）—— 它们能"成功"
产出一张糊图，把"这张壁纸没有可用画面"这个**可判定事实**退化成看似正常的画面。

**仍在生效的裁定**：

1. **档位值域 `{0, 4}`**（0 = 自动求链头；4 = 强制自定义画面且**豁免**抓帧）。`1/2/3` 与越界值 clamp 到 0
   ⇒ 旧配置原样可用，那条 pin 降级为"自动"（唯一可接受的降级方向）。值域里的洞有意保留（可读性）。
2. **零迁移只在客户端做**：`frameVariants` / `customFrames` 是客户端独占键（`verify-client` 的
   `CLIENT_ONLY`），宿主白名单不动 ⇒ clamp 落在客户端 `sanitizeSettings`。
3. **缓存键**：`LIVE_FRAME_KEY_VERSION = 'lf1'`（原 `SCENE_FRAME_KEY_VERSION = 'sf34'`）。移除提取链后
   目录里只剩 `_gpu.png` ⇒ 升值的代价从"全库重提取"降为"重抓几张帧"。
4. **三种「预热」的去向**：① 宿主静态帧预提取 **已删除**（它 import 的正是被删的提取链）；
   ② 轮换的 live 预载 **仍在、且更重要**（live 是唯一动态来源）；③ 手动切换的 live 启动仍缺 ——
   裁定过的"把抓帧延后到 t≈N"**未启用**（N=0，行为不变）。
5. **URL 与命名**：`/scene-frame` **不改名**（兼容零风险）；`?v=` 保留；③ 排在 ④ 之前（与
   `gpuFrameFileFor()` 一致）。§6.14 其余未决项均按当时的默认执行。
6. **首帧之前的垫底画面**：来源顺序 = **实时抓帧 → 作者随包发布的工程预览图 → 主题色**
   （客户端 `buildLivePoster`）。预览图**只作占位**，不破上面那条"不替作者猜一张图"的裁定：
   `/scene-frame` 在没有帧时**仍给 404 空态**（服务端一个字节都不变），预览图从不被当作"这张壁纸的
   出图"，live 首帧（`.we-live-on` 淡入）一到就被顶掉。**第二级不可省**：抓帧要等本轮 live 回填才
   存在，只试一级会 404，而失败是"静默保留主题色"（近黑）⇒ 首帧前就是黑屏。判据：
   `rotation-prepared-leak-smoke` 的 P / P2（正 / 负对照成对）。

**守卫**：反向探针（`renderSceneFrameInWorker` / `extractSceneMainImage` / `collectImageObjectTextures` /
`sceneFramePrewarm` 等标识符零残留）在 `test/verify-retired-lines.mjs`；语义断言（clamp、`v=4` 豁免、
空态不回落）在 `test/verify-scene.mjs`。两者均已绿。

### 9.5 数据与文件（F3）

| 落点 | 内容 |
|---|---|
| `lib/fontsets/<id>.json` | **随包层**（发布物，**只读**）：开箱就有的少量预设 + 可分享的正文格式；用户改它 ⇒ 写时复制到下一行 |
| `~/.dsh-wallpaper-engine/fontsets/<id>.json` | **用户层**（可写）：导入、覆盖、一次性迁移的产物 |
| `~/.dsh-wallpaper-engine/config.json` | **只记** `{ fontSetId, fontCustom }`（`fontSetId` 是根字段） |

**客户端侧**：字体值走**另一条**通道 `src/fontset-store.js`（与 `src/persistence.js` 同形但真源不同）—— 启动链 `loadPersisted → loadFontSet → loadInventory`；宿主那份**一次 `Object.assign` 整套采用**，读不出来时**整套不动**（保留本地缓存那份）并留可判定文案；本地缓存键 `we-fontset-active`（与设置缓存分开）。

**两层优先级**：同一 id **用户层胜**；`activate` 是唯一改指针的写原语（将来按条件自动选预设是**策略层**，必须调同一个原语 —— 指针保持单一真源）。随包层删不掉（可覆盖），删掉覆盖 = **恢复随包原样**。

**理由**：localStorage 只有 5MB；宿主白名单漏键会**静默丢弃**（= R4）；滑杆每次回调都同步写 settings 太重。
导入导出复用 `/upload` + 数据目录 + 文件选择器的现有基建（F3 因此依赖 P2-9）。

### 9.6 红线（违反即回归）

1. **白闪红线**：不得引入 `:has()` / 祖先相关选择器；作用域只用属性/类**直接命中**。
2. **令牌层不写 `!important`**；body 默认层维持现状（只在 body 上用）。
3. **不抢** `--dsh-content-font-size`（那是 DSH 自己的字号设置）。
4. **`.we-*` 插件自身面板默认不跟随**（否则用户会把设置面板调糊）。
5. **readability floor 必须保留**：颜色角色化后更容易调出不可读组合 ⇒ 面板对越界值给提示。
6. **令牌名漂移**：未知令牌**静默忽略**；面板对"当前 DSH 不存在的角色"**置灰**。
7. **回落通道**：`theme` 注入失败 ⇒ 回到 `/style` 注入路径（**保留双通道**，按能力探测）。

### 9.7 已执行的决定（留档一句话）

当时的待拍板项均按推荐项执行；F3 是最后落地的一项（见 §9.5）。与重构账本的耦合顺序（F1 排在 P1-5
之后、F3 依赖 P2-9/P2-10）已兑现 —— 顺序**不再是约束**。
