## 怎么复现

```
node scripts/profile-scene.mjs <workshopId> [宽] [高] [时间秒] [--gpu|--cpu]
# 例（用户库最慢的几个）
node scripts/profile-scene.mjs 3582367840 3840 2160 2.5
```

剖析由 `DSH_WE_PROFILE=1` 驱动（`lib/we-renderer/profile.js`），默认关闭时零计时开销。

## 二、三个被数据推翻的假设

**① "降低渲染分辨率能提速" —— 不成立。**
同一场景 3582367840，输出从 3840×2160 降到 960×540（像素数 1/16）：

| 效果 | 3840×2160 | 960×540 |
|---|---|---|
| godrays | 2374ms | 2362ms |
| blurradial | 2088ms | 1871ms |
| waterwaves | 1237ms | 1296ms |
| shimmer | 522ms | 579ms |
| watercaustics | 534ms | 545ms |
| **整帧渲染** | **9860ms** | **8235ms** |

整帧只快 16%，效果耗时几乎不变。**效果内核跑在图层纹理上，与输出画布分辨率无关。**

**② "PNG 编码/落盘是大头" —— 不成立。** 140–899ms，占比 4–19%。

**③ "砍'不涉及位置变化'的效果最省" —— 不成立。**
最贵的两个家族都被点了名：

- **位移类**：`waterflow` 5084ms(2×8.68Mpx)、`shake` 3421ms(33.18Mpx)、`waterripple` 1280ms、
  `waterwaves` 1235–1350ms、`depthparallax` 936ms
- **纯观感类**：`godrays` 2374ms、`blurradial` 2088ms、`watercaustics` 534ms、`shimmer` 522ms

共同点不是"是否位移"，而是**输入纹理大**。按"是否改变位置"分类无法预测成本，
据此做 UI 开关会砍错对象。

## 三、真实成本模型

```
效果耗时 ≈ Σ (该效果的输入纹理 Mpx × 该内核每 Mpx 成本)
```

每 Mpx 成本实测相差近 6 倍（最重 ≈ 最轻的 5.8 倍）：

| 内核 | 每 Mpx 成本 |
|---|---|
| `waterwaves` / `foliagesway` | ~85–100 ms/Mpx |
| `shake` | ~103 ms/Mpx |
| `waterflow` | ~293 ms/Mpx |
| `godrays` | ~401 ms/Mpx |
| `blurradial` | ~494 ms/Mpx |

而输入纹理尺寸跨度极大——`3669681034` 有一个 **33.18 Mpx** 图层（8192×4096，即
解码后 ~146MB 的那张 8K 主纹理），单是 `shake` 就 **3421ms**；其余场景多在 2–9 Mpx。

**所以只有两个杠杆**：

1. **减少送进效果的 Mpx** —— 纹理侧降采样 → 跑效果 → 上采样回原尺寸。
   代价随缩放平方下降（1/2 边长 → 1/4 耗时，1/4 边长 → 1/16）。
   godrays/blurradial/shimmer/watercaustics/水波/视差都是低频效果，画质损失小。
2. **跳过效果** —— 收益最大但画面确实变了。

## 四、已有但未接线的机制（重要）

这套代码里降采样**已经写好，只是没接上**：

- `lib/we-renderer/core.js:829 _downsample(tex, maxSize)` —— **零调用方**。
  注释写着"效果/渲染前把大纹理缩到 maxSize, 提速 CPU 逐像素"。
- `lib/we-renderer/render/framebuffer.js:48 downsampleImage()` —— **零调用方**。
- `lib/we-renderer/glsl/integration.js:147-156` —— GLSL 效果的降采样路径**存在**，
  但被 `!this.staticFrame` 挡住，注释为"静态帧不应用降低分辨率操作"（用户要求）；
  且阈值 `MAX_GLSL_PIXELS = 65536`（256×256）相当激进。
- `lib/we-renderer/glsl/integration.js:211 _upsampleRgba()` —— 已实现，可用。
- `core.js:61-63` 把 `staticFrame` 设为"非多帧"，并注明静态帧**刻意不降采样**
  （"4K 壁纸效果全分辨率保证细腻"）。

也就是说：**用户实际等待的那条路径（单帧静态帧）恰恰是唯一没有降采样的路径**，
而降采样只写在多帧动画分支的意图里。注意上面第 2 条实验表明，这个"全分辨率"
选择保的是**输出锐度**，它几乎不增加效果耗时——真正决定耗时的是纹理侧，两者不冲突，
所以"输出仍出全分辨率、只在跑效果时缩纹理"是可以同时成立的。

## 七、内核微优化：实测没有空间

原以为 `blurradial` 494ms/Mpx、`godrays` 401ms/Mpx 是"实现写得慢"。实测否掉了。

采样原语 `_texSampleInto` / `_texRG` 的裸吞吐（`scripts/tmp-bench-sampler.mjs`，4096×4096）：

| 变体 | ns/采样 |
|---|---|
| 现版 `clamp=true` | 30.2–31.0 |
| 现版 `clamp=false`（wrap 路径） | 54.0–54.2 |
| 手写展开 4 通道（`clamp=true`） | 31.7–32.0 |

线上 `blurradial` 折算约 62ns/采样（494ms/Mpx ÷ 每像素 8 次采样），而裸采样
`clamp=false` 就是 54ns —— **内核本身几乎没有开销，它就是采样本身**。
而手写展开 4 通道 **零收益**（31.7 vs 30.2，V8 早已处理），说明"把循环展开 / 少调
Math"这类微优化没有空间。

**唯一实测到的无损空间在网络之外**：wrap 归一化 `((u%1)+1)%1` 因为两次取模要
12.6ns，换成数学等价的 `u - Math.floor(u)` 只要 **2.1ns（5.8x）**。
`clamp=false` 的采样会因此从 54ns 降到约 35ns，对 wrap 路径为主的效果约 **1.5x**。

> 等价性注意：5 万组取值中有 3 组相差 1 ULP（`u=0.1/0.9/0.0001`，Δ≤1.11e-16），
> 且方向是**新写法更准**（旧的双取模在已归一化的值上引入浮点误差）。
> 坐标级不等不必然产生像素级差异，但本项目是逐位对齐的，需用 `verify-scene` 做帧级 A/B。

## 八、GPU 路径实测：后端完好，缺的只是适配层

`gpu-diag.log` 初看像是"GPU 时灵时不灵"，实际查下来是**结构性问题**：

全仓库搜索 `_tryEffectGpu` / `_tryEffectChainGpu` / `_getGpuBackend` / `_dawnEffectCache`
—— 这 4 个符号**从未被定义过**，只有引用：

| 引用位置 | 性质 |
|---|---|
| `render/passes.js` | 死文件（零调用方），引用 4 个符号 |
| `scene-render-worker.mjs:92,127,144` | `renderer._getGpuBackend ? ... : 'n/a'` —— 存在性守卫，故当前 HEAD 恒为 `n/a` |
| `core.js:60` | `this.gpuAccel = opts.gpuAccel === true` —— **赋值后无人读取** |

`git log -S` 显示这些符号随"移除 scene-anim 动画方向，聚焦静态帧"重构一起消失，
但引用方被留下了。`gpu-gl/`、`gpu-dawn/` 只被 worker 用于**释放**（`disposeGPU`）
和启动时**探测**，渲染路径从不经过它们。

**但后端代码是完好的。** 直接调 `runEffectOnGL`（绕过被移除的适配层）实测
（`scripts/tmp-gpu-probe.mjs`）：

```
getWebGL(true) = OK
identity 正确性: 64x64  maxΔ=0  平均Δ=0.000        ← 逐字节一致
4K identity pass: 13.1 / 17.2 / 24.4ms  ⇒ 1.6–2.9 ms/Mpx   (含 FBO + readPixels 回读)
```

对照 CPU：单次采样 4K 约 250–450ms（§七 的 30–54ns/采样）。**GPU 快 15–30 倍，
且逐字节一致。** 也就是说这不是"要复活一个坏掉的功能"，而是"把一层几十行的
适配层接回去"——`runEffectOnGL` / `runEffectChainOnGL` / `runRenderEffectsOnDawn`
入口都在，`gl-shim.js`（`toWebGLSource`/`needsShim`）负责 WE shader 转译。

需要一并处理的既有耦合：

- UI 里"GPU 渲染加速"开关**存在**（`client.js:3442`），但被 `betaSceneAnim` 挡着，
  且它开关的东西不存在 —— 用户看到的是个空开关。
- `gpuFlag` 进了帧缓存键（`index.js:981`、`3026`），**切换这个空开关会作废帧缓存**。
  这可能就是"缓存全部失效"的一部分来源。
- `findGpuNodePath()` / `probeNodeAbi()` / fork 系统 Node 的整套装置
  （`index.js:1000-1080`）是为 GPU 服务的；因为 GPU 没接线，它当前只在
  `gpuAccel` 被请求（且再被 `betaSceneAnim` gate）时空转。

## 九、方案空间（纹理降采样已否决）

用户已确认**纹理侧降采样是被放弃的路线**（极度破坏观感），相关逻辑只是没删。
把它移出选项后，成本模型 `Σ(纹理 Mpx × 内核成本)` 里 **Mpx 这一项就固定了**——
剩下唯一的无损方向是**把这份固定工作量摊到更多计算单元上**。

### 可行

| 方案 | 预期收益 | 代价 / 风险 |
|---|---|---|
| **① 接回 GPU 适配层** | **15–30x**（已实测，且逐字节一致） | 后端完好、入口齐全（§八），缺的是把 `_tryEffectGpu`/`_tryEffectChainGpu`/`_getGpuBackend` 定义回 `SceneRenderer` 原型并让 `applyEffects` 走它。风险在 WE shader → WebGL 转译覆盖率：转不了的必须返回 null 回退 CPU（这正是原设计）。另需在系统 Node fork worker 内运行（ABI），故 `findGpuNodePath` 那套要保留 |
| **② 效果内核多线程** | **~5–8x**（24 逻辑核，现为单线程） | 内核是纯逐像素映射、按行独立 ⇒ 天然可并行。需在 `scene-render-worker.mjs` 侧加线程池 + `SharedArrayBuffer`；受内存带宽限制拿不到 24x；小 pass 需设像素阈值避免调度开销 |
| **③ wrap 归一化替换** | 1.2–1.5x（wrap 路径 1.5x） | 2 行改动、无算法风险；需帧级 A/B 确认 1 ULP 不改变输出像素 |
| **④ 空闲预热 + 按需渲染队列** | 不改渲染速度，改"谁在等" | 把 10s 从用户眼前移到空闲时段。与 ⑤ 互补 |
| **⑤ 首帧垫图 + 后台升级** | 消除"黑色 10 秒"的感知 | 用户之前踩过"preview 被当成壁纸本体"的坑；现在语义已定为"帧才是壁纸"，可做干净：立即显示主纹理/上一张好帧，真帧算好替换，**interim 绝不落盘成正式缓存** |
| **⑥ 管线版本升版策略** | 消除批量重渲 | `sf33 → sf35a` 一次性作废 101 张缓存，是"整体体验倒退"的直接成因。可保留旧帧作 interim，或增量重渲 |

### 已排除

- **纹理降采样** —— 用户已否决（破坏观感）。
- **降低输出分辨率** —— 实测无效（§二①），效果耗时与输出分辨率无关。
- **输出分辨率降采样** —— 无效，同上。
- **内核算法/微优化** —— 实测无空间（§七），已到裸采样吞吐。
- **PNG 编码优化** —— 只占 4–19%，上限有限。
- **按"是否位移"做 UI 开关** —— 分类维度错误（§二③），会砍错对象。
- **死代码清理** —— 不是性能方案，但 `passes.js` / `registry.js` / `framebuffer.js` /
  `_downsample` 四条零调用方路径应清掉，避免后续改错文件（我一开始就把埋点加错在
  `passes.js` 上，跑出零样本才发现）。

### 建议顺序

**① 接回 GPU 适配层** —— 实测 15–30x 且逐字节一致，是性价比最高的一条，优先做；
顺带清掉"GPU 开关可点但无效 + 切换即作废帧缓存"这个用户可见的问题。

**② 多线程** 作为 GPU 转译覆盖不到的那部分效果的兜底（GPU 不能保证覆盖全部 WE
shader），也是不依赖 GPU 环境的确定性提速。

**③** 是顺手的廉价补充。**④⑤⑥** 属体验层，可独立于渲染速度推进。

## 十、"快速模式"实测：跳过效果 vs 切主纹理回退

问题：能不能做一个 UI 开关，人工实现当年那个"静默回退主纹理"的效果——不再挑具体
效果，而是**从一开端就不启用效果计算**？

答案：**可行，而且应该实现成"跳过效果链"，不要实现成"切到主纹理合成"。**
两个候选都实测了（4K 冷启动，`DSH_WE_NO_FX=1` 为诊断短路开关）：

| 场景 | 完整渲染 | ①不跑效果 | 省下 | ②主纹理合成 |
|---|---|---|---|---|
| 3582367840 | 9860ms | **2617ms** | 73% | 2750ms |
| 3554161528 | 8191ms | **1648ms** | 80% | 2333ms |
| 3669681034 | 4704ms | **1940ms** | 59% | 2559ms |
| 3461168300 | 5718ms | **2524ms** | 56% | 2980ms |
| 3486806915 | 4122ms | **3433ms** | 17% | **12330ms** |
| 3641860575 | 2205ms | **983ms** | 55% | 688ms |

### ① "不跑效果" = 完整渲染器照跑，只是永不进 `applyEffects`

- 5/6 个场景省 **56–80%**，最慢的从 9.9s 掉到 2.6s。
- **没有效果分类问题** —— 你要的"不再考虑具体的效果"就是这个语义。
- 构图、位置、puppet、粒子、文本、相机、脚本**全部保留**，只丢效果观感
  （水面波纹、godrays、bloom、shake、视差等）。
- 实现就是 `effects.js::applyEffects` 开头一个短路判断（本次诊断已经这么做），
  加一个设置项 + 缓存键位。

### ② "主纹理合成"（现有 `.fb.` 回退路径）

它**不是**取一张贴图——`pkg-extract.js:1428 extractSceneMainImageVia` 是一套
**独立的无效果合成实现**：遍历 scene 对象 → 每层 `resolveObjectTransform`
→ `resizeBilinear` → `blitLayer` alpha 合成 → clearcolor 填充 → 质量门 → PNG。
产物名 `composite(N layers)`。

- 只处理**带贴图的 image 层**；不含 puppet/模型/粒子/文本/相机/效果。
- 是渲染器之外的第二套合成实现（有漂移风险）。
- 成本不低且不稳：688ms–**12330ms**。`3486806915`（43 层）要 12.3s，
  **比完整渲染（4.1s）还慢 3 倍**，而它的"不跑效果"只要 3.4s。
- "0.7.3 秒开"来自**缓存命中**，不是来自这条路径本身快。

### ⚠️ "全跳过"必须留一个极小的例外集（正确性，不是调优）

`image.js:205-248` 的 `_renderSolidLayer`：作者纯色层（窗户/窗帘/树叶/云）的**画面本身
来自效果链** —— `texture_override` 把 PNG 贴到纯色四边形上。注释原文：

> 效果是逐像素处理的 (texture_override 的 UV = f(uv, g_offset, 输入/覆盖分辨率) …)
> 1×1 输入时所有效果都退化成单点取值 ⇒ 该层永远是一个**均匀色矩形**
> (实测: 窗户/窗帘/树叶/云的"矩形纯色块")

所以**全跳过效果会让这类层退化成矩形色块** —— 正是 PR #88 修掉的那一类 bug。

必须保留的例外只有**塑形类**：`texture_override`、`custom_user_texture`
（以及 `instanced` 纯色层的塑形效果；`image.js:240` 已有 `fxStatus.produced`
守卫，跳过时该层整体不绘制，方向是安全的）。

**这不是"按成本挑效果"** —— 是"不跑它们画面会坏"。两个名字 vs 之前那 25 个的分类
问题，性质完全不同。而它们恰好也是便宜的（逐像素贴图混合，同 tint/opacity 量级，
约 100–300 ms/Mpx），留着几乎不花钱。

### 结论

**①全面优于②**：保真更高（真渲染器的构图 vs 第二套合成的近似）、成本更低或相当、
且不引入重复实现。②应继续只当**错误兜底**，不要升级成用户模式——它的
`.fb.` / `FALLBACK_RETRY_MS` 语义都建立在"这是失败产物"之上。

### 这个开关顺带解决一个旧坑

你之前踩过"等待期垫图，结果 preview 被当成了壁纸本体"。做成**显式模式**后，
两种模式各有自己的缓存键，快速帧是**一种正式产物**而不是伪装成正式帧的垫图。

进一步可做**两段式**（可选）：先出①（无效果）立即显示 → 后台算完整效果帧 →
算好后替换；两帧各自独立缓存。这样既秒开又不丢效果，且语义干净。

## 十一、独立"无计算渲染层"评估

提案：不复用现有实现，另做一个**独立的无计算渲染层**作为快速路径。

### 0.7.3 与 0.7.4 的回退动作确实不同（已核实）

`pkg-extract.js` 里 0.7.3(`8a0d1d8`) → HEAD 对回退路径**唯一的改动**是新增
`downsampleRgba` + `capFallbackFrame` + `FALLBACK_MAX_WIDTH = 3840`（67 行，
提交 `2d17fd5` / #88）。`tryCompositeSceneLayers` 本体没动。

- **0.7.3**：`extractSceneMainImage` **不封顶** —— 可产出 8192×4680（解码 146MB）
  的巨图，正是上游 #86 的内存/显存与启动卡顿来源。
- **0.7.4+**：同一条路径，但限幅到 3840 宽。

但 `lib/index.js` 在同期改了 **1189 行**（`.fb.` 独立命名、`FALLBACK_RETRY_MS`
重试 TTL、取消语义、后台探测）—— **"缓存全部失效、逐个点击重载"来自这里，
不是来自这条路径渲染什么**。

### 支持独立层的理由（比"更快"更硬的两条）

1. **缓存稳定性** —— 无效果层的输出不依赖效果管线。现在帧缓存键含
   `PIPELINE_VERSION`（`sf35a`），渲染器一升级全库作废；无计算层可以用
   **独立且稳定的命名空间**，升级不再作废它。直接打在最大痛点上。
2. **不需要例外清单** —— §十 说"跳过效果"必须保留 `texture_override` 等塑形类
   （否则纯色层变矩形色块）。而独立层**只合成真实 image 层**，压根不画纯色层，
   天然没有这个问题。比"渲染器跳效果"更简单。
3. 附加：无效果层的产物与时间无关、与脚本无关，可在**扫描期/后台预热**，
   把"逐个点击重载"变成一次性预热。

### 必须处理的三个问题（实测）

**① 性能——现有 composite 的慢是自找的。**
`pkg-extract.js:1403-1414` 对每一层先 `resizeBilinear` 生成一份**整层大小**的中间
RGBA 缓冲，再 `blitLayer` 拷一遍 —— 每层两趟 + 一次大分配。渲染器走的是
`blitScaled` 一遍完成。改成一遍带缩放 blit 应能大幅下降（43 层那例 10.8s，
而真渲染器做同样多的解码 + 更多光栅化只要 3.4s，说明瓶颈在这两趟）。

**② 覆盖率与保真上限——不能保证有产物。**

本地 16 个含 `scene.pkg` 的场景实测：

| 路径 | 场景数 | 成本范围 |
|---|---|---|
| composite（多层） | 7 | 600ms – **10774ms** |
| 单贴图 | 8 | 68ms – 1575ms |
| **质量门拒收（无产物）** | **1** | 3640755971: `gray=100% var=31.1` |

- 产物尺寸跟随场景声明投影，**不一定是屏幕宽高比**（实测有 3840×576、2880×1800、
  2304×1296），作背景需要额外的适配策略。
- `pkg-extract.js:1243`：只要有**任意** `model` 对象就整体 bail out 退回单贴图 ——
  puppet / 模型 / 粒子 / 文本 / 相机一律不含。
- 质量门会拒收整帧 ⇒ 独立层必须自己保证非空产物（退回"任一可解码贴图"）。

**③ 已经是两份，而且分叉了。**

| 文件 | model-bailout | 8K 像素上限 | 质量门 | 状态 |
|---|---|---|---|---|
| `pkg-extract.js:1240` | 有 | 有 | 有 | **线上走这份**（`index.js:3065`） |
| `scene-manifest.js:1332` | 无 | 无 | 无 | index.js 不 import |

做独立层应**合并这两份**（从 2 份变 1 份），而不是再加第三份。

### 建议形态

```
lib/scene-still.js            独立无计算渲染层
  输入  scene.pkg → 输出 {width,height,rgba} + {layerCount, kind}
  只做  静态 image 层: 定位 / 缩放 / alpha / crop + clearcolor
  不碰  effects / puppet / model / particle / text / camera / scripts
  实现  一遍 blit-with-scale (去掉 resizeBilinear 双趟)
  缓存  独立命名空间 still_v1_<b64>_<mtime>, 不随 PIPELINE_VERSION 失效
  产物保证  质量门拒收时退到"任一可解码贴图", 绝不返回空
  合并  让现有错误兜底也调它 (吃掉 scene-manifest.js 那份)
```

### 需要定的问题

独立层的契约选哪个？两者不冲突，可以并存：

- **A 纯静态图层合成**（本提案）：不含 puppet/粒子/文本/相机。便宜、语义简单、
  缓存稳、无需例外。代价：本地 8/16 场景只有单贴图，角色类壁纸会明显退化。
- **B 完整渲染但永不进效果**（§十 的①）：保真高得多，最慢场景 3.4s
  （比 composite 的 10.8s 快 3 倍）。代价：缓存绑 `PIPELINE_VERSION`，且需要
  塑形类例外清单。

数据上 B 在"保真 + 层多场景的速度"更好，A 在"语义简单 + 缓存稳定 + 无例外"更好。
合理分工是 **A 当秒开兜底、B（+§八 的 GPU）当最终画质**。

### ① 的三个"问题"，只有两个算 bug

| 问题 | 性质 | 依据 |
|---|---|---|
| `instanced` 纯色层白方块 | **是 bug，且已有修复 + 护栏** | PR #88 标题含 "solid layer 白方块"；`image.js:240` 的 `fxStatus.produced` 守卫就是那次修复。① 重新触发 = **回归**，修它算 bugfix |
| `texture_override` 退化成纯色块 | **是 bug 类，但根因是架构不是缺陷** | 见下 |
| 缓存键绑 `PIPELINE_VERSION` | **不是 bug，是设计取舍** | 键含管线版本是**故意**的（注释："管线变化就必须自增, 否则旧产物继续被命中"）。① 的缓存不稳是"共用同一键空间"的必然结果，只有**独立命名空间**能解 |

**为什么 `texture_override` 这条不能小补丁修掉。** 该文件自述："GLSL 解释器失败时若不做
原生实现, 这些组件会退化成纯色块 (白块)" —— 它本身就是修 bug 的产物。而它之所以必要，
是因为官方语义就是"图层先渲到四边形尺寸的 RT → 效果链处理 → 合成"，即
**图层内容本身来自效果链**。这是官方语义，不是缺陷。

所以只有两条路：

- **保留 2–3 个塑形类名字**。实测本地库 **4/16 场景**用到（`3629379075`、
  `3640755971`、`3641860575`、`3660962877`：`texture_override` /
  `custom_user_texture` / `user_texture_alpha_overwrite_workaround`）。
  不是理论问题，是要真背的。
- **根因重构**：把图层的基贴图在**加载期**解析（像 image 层那样），让内容不再依赖
  效果链。**这才是真正的 bugfix**，而且能让白方块类问题**结构上不可能**出现，
  而不是靠 `fxStatus.produced` 兜住。代价：会改像素（底色非白 / `BLENDMODE` 非
  multiply / 一个对象挂多个 override 时），必须帧级验证。

**更正一（上轮估计过悲）**：`pkg-extract.js:1243` 只要有任意 `model` 对象就整体 bail out

## 十二、多层合成：两趟 + 大分配已修，但它不是瓶颈

用户指出的问题成立并已实现修复，但**测量推翻了"它是主要成本"这个前提**。

### 改了什么

`pkg-extract.js` 的合成循环原先每层走
`resizeBilinear(...)` → `blitLayer(...)`：① 分配一份**整层尺寸**的中间 RGBA 缓冲
并写满，② 再从头读一遍做 alpha 合成，且遍历的是**整层**（画外部分白算）。

新增 `blitLayerScaled()`：把双线性重采样结果**直接就地合成**，且只遍历
图层矩形 ∩ 画布。两条采样/舍入表达式（含运算顺序）逐字保留，故输出不变。
旧的 `resizeBilinear` 随之无调用方，已删除（不留死代码）。

## 十三、真正的大头：合成路径没有解码缓存

按"先剔除离屏层"的建议推进时，先做了一次对照测量，结果**推翻了上一轮的判断依据**。

### 先纠正一个错判

上一轮我写过"渲染器解码 47ms/张、合成 207ms/张，同样贴图慢 4.4 倍"。**这个比较是错的** ——
它比的是两批不同的贴图，不是两条代码路径。在同一批贴图字节上直接对照
（`scripts/tmp-decode-compare.mjs`，65 张贴图各测两条路径）：

```
可解码 65 张:  合成路径合计 1988ms (31ms/张)   渲染器路径合计 2264ms (35ms/张)
```

**两条路径速度相同**（比值 0.8–1.0，合成甚至略快，因为它用了 `useTArray`）。
解码慢不是代码路径的差异。

### 真正的原因：同一张贴图按引用次数重复解码

`3486806915` 全部 65 张贴图各解一次只要 **1988ms**，而合成报告的解码是 **8891ms**。
差 4.5 倍。对着贴图清单一看就清楚了：

| 贴图 | 尺寸 | 单次解码 | 占全部解码 |
|---|---|---|---|
| `鸟_00020.tex` | **7680×7920**（6080 万像素） | **1308ms** | 65.8% |
| `栏杆.tex` | 3328×2176 | 193ms | 9.7% |
| `背景.tex` | 3840×2176 | 189ms | 9.5% |

`680 + 1308 × 6 = 8528 ≈ 8891` —— **`鸟_00020` 被 6 个对象引用，就被解码了 6 次。**
合成路径**没有解码缓存**（渲染器有 `textureCache`），每引用一次就 `access.readFile`
+ `decodeTexToRgba` 一遍。

### 修法

在 `tryCompositeSceneLayers` 内加一张 `texPath → 解码结果` 的 Map（本次调用内复用）：
命中时**连 pkg 读取一起跳过**。

不变量（为什么共享是安全的）：缓存的是**解码结果本身**，`cropoffset` 分支只派生新的
`img` 对象、从不原地改缓存内容，`blitLayerScaled` 只读不写。日后若有人在本路径上
原地改 `L.img.rgba`，这个共享就会变成别名 bug —— 已在代码注释里写明。

### 副效益：峰值内存从 ~1.4GB 降到 ~232MB

这一条可能比提速更重要。修改前，被 6 个对象引用的 `鸟_00020` 会各自解出一份
`7680×7920×4 = 232MB` 的 RGBA 并在 `layers` 里**同时持有到 pass 2**：

```
232MB × 6 = 1.39GB    (仅这一张贴图, 尚未含其余 42 层与 3840×2160 画布)
```

修改后是同一份 232MB 共享。峰值内存下降约一个数量级，GC 压力与潜在的换页随之消失 ——
这很可能就是"有些场景陷入很长时间的等待依旧没有效果"的成因之一。

|---|---|---|---|---|---|---|
| 3486806915 | 43 | 10757ms | 9660ms | **2926ms** | **3.68x** | 9 |
| 3582367840 | 13 | 2653ms | 2011ms | 1691ms | 1.57x | 3 |

| 3554161528 | 8 | 2031ms | 1668ms | 1564ms | 1.30x | 0 |

### 这条路径现在还剩什么

`3486806915` 修后 3003ms 的构成：解码 2023ms（67%）、重采样+合成 542ms（18%）、
PNG 编码 397ms（13%）。解码 2023ms 已经 ≈ 唯一贴图理论下限 1988ms
（34 张唯一贴图），**这条路径基本榨干了**。

剩下唯一的大头是 `鸟_00020.tex` 那 **6080 万像素、单张 1308ms** —— 占整个合成 43%。
它的图层实际绘制尺寸远小于纹理本身，但当前必须先全分辨率解码再重采样。
要再往下走只能是**按目标尺寸做缩放解码**（DCT 缩放 / DXT 分级解码），
那会改变输出像素（略微变软），属于观感取舍 —— **不在本轮范围内，待你决定**。

原先建议的"剔除离屏层"在解码缓存之后边际收益已很低：现在只剩 34 张唯一贴图，
其中最大的一张（鸟）显然是画面主体，剔除离屏省的顶多 200–300ms，
却要引入"解码前就要知道尺寸"的复杂度与逐位一致风险。**建议不做。**

## 十四、GPU 适配层：已接回，但被两个拦路问题压住

### 做了什么

- `lib/we-renderer/gpu-gl/adapter.js`（新）：补回 `_getGpuBackend()` /
  `_tryEffectGpu()`，在 `core.js` 里 install。
- `glsl/executor.js`：`compileGlsl` 现在一并返回 `fragPre` / `vertPre` ——
  **GPU 与 CPU 共用同一份预处理结果**，include 展开 / combo 宏不会两侧分叉。
- `effects.js::applyEffects`：CPU 分支前先试 GPU，失败返回 null 即自然落回 CPU；
  退化保护、scratch 归还、逐效果计时全部沿用同一套。
- 开关：沿用 `SceneRenderer.gpuAccel`（`opts.gpuAccel === true`），**默认关闭**。
- 回退与熔断：无 headless-GL/驱动 → 状态锁 `off` 直接返回 null（零重试开销）；
  连续 3 次失败 → 熔断，本进程内全部回退 CPU。**GPU 不可用绝不影响渲染可用性**
  —— 实测无 assets 时 3 次编译失败即熔断，渲染照常完成。
- 只接**单效果** GPU 执行；`runEffectChainOnGL` 未接 —— 那段链式代码
  （`sceneTexUnit` 附近）看起来是半成品，不值得冒险。

### 实测（`3486806915` @1920×1080，带 `weAssetsDir`）

```
gpuBackend=true   走GPU效果数=24   失败=1
CPU 5887ms   →   GPU 5611ms     提速 1.05x
```

**几乎没有提速**，原因很具体：

| 效果 | CPU | GPU 运行 | 说明 |
|---|---|---|---|
| `color_grading` | 1973ms | **1965ms** | **链接失败 → 仍走 CPU**，占全帧 35% |
| `foliagesway` | 467ms | 178ms | 走成 GPU，2.6x |
| `opacity` | 336ms | 394ms | 走成 GPU 但**更慢**（上传+回读 > 计算） |
| `waterwaves` | 236ms | 192ms | 1.2x |

### 拦路问题 1：`color_grading` 链接失败

```
program 链接失败: Types of varying 'v_TexCoord' differ between VERTEX and FRAGMENT shaders.
```

该效果自带 `.vert`，其 `v_TexCoord` 类型与 frag 声明不一致，WebGL 拒绝链接。
CPU 解释器不关心这个（它自己插值 varying），所以 CPU 能跑而 GPU 不能。
**这是全帧最大的单个效果（35%），不修它 GPU 等于白接。**

### 拦路问题 2：输出可见差异

同场景两种模式的 PNG 对照：

```
逐像素最大通道差: 平均 2.097   最大 249
  >2 : 5.716%    >8 : 3.869%    >32 : 2.039%
```

**2% 的像素差异超过 32/255 —— 肉眼可见。** 最可能的原因正是 adapter 注释里预告
的那条：CPU 解释器对**辅助槽纹理**用 REPEAT（`__glslRepeat`），而
`uploadTextureData` 对所有纹理统一 CLAMP_TO_EDGE。`opacity` 的 mask 采样就属于
这一类。修它要按槽位区分 wrap，而 gpu-gl 里纹理按 `texData` 对象全局缓存，
同一张纹理可能同时当主图（CLAMP）与辅助槽（REPEAT）—— 简单改会串。

### 结论：开关已可交付，但默认必须保持关闭

回退链路健全、开关独立、verify 全绿；但当前**1.05x 收益 + 2% 像素可见差异**
这个组合不该默认开启。要让它真正有价值，须先解决拦路问题 1（varying 链接）与
2（wrap 语义对齐）——两件都是独立、可验证的活，建议按此顺序做，做完再重测。

### 后续进展：拦路问题 1 已解决，2 被证伪

**问题 1（varying 链接）—— 已修。** 根因是 WE 的 frag/vert 对同名 varying 类型不一致：

```
color_grading.frag:  varying vec2 v_TexCoord;
color_grading.vert:  varying vec4 v_TexCoord;   // 只写 .xy = a_TexCoord
```

CPU 解释器不检查（自己插值 varying 并按分量取用），WebGL 直接拒绝链接。
修法：在 `buildProgram` 里加 `reconcileVaryings(fSrc, vSrc)` —— **以 fragment 的声明为准**
改写 vertex 侧声明（frag 用不到的 zw 对语义无影响）；仅当 vert **未引用**将被丢掉的
分量时才降级，有引用就保持原样让链接失败自然回退 CPU。
顺带修掉 `defaultVertFor` 的同类 bug：它对声明 `vec2 v_TexCoord` 的 frag 一律赋 `vec4`，
这类 shader 在无自带 vert 时也会编译不过。

效果（`3486806915` @1920×1080）：

| | 修前 | 修后 |
|---|---|---|
| 走 GPU 效果数 | 24 | **25** |
| 失败 | 1 | **0** |
| `color_grading` | 1965ms（仍在 CPU） | **249ms** |
| 整帧 | 5611ms（CPU 5887ms） | **3894ms** |

**CPU 5887ms → GPU 3894ms = 1.51x。**

**问题 2（wrap 语义）—— 已实现但被证伪为主因。** 按槽位对齐了 wrap
（`g_Texture0` CLAMP、辅助槽 REPEAT，与 `integration.js` 同一套 `__glslRepeat` 标记），
但输出差异**一位小数都没变**：平均 2.103、`>32` 2.039%（与修前完全相同）。

所以 wrap 不是主因。更合理的解释是：**GPU 跑的是官方原始 shader，而 CPU 对这些
内置效果跑的是手写移植实现** —— 两者本就该有差异，这不是浮点噪声，而是"两套实现"。
这解释了为什么差异稳定且不随 wrap 变化。

**当前状态**：`verify` 全绿；GPU 关闭时 CPU 路径两次运行逐位一致（无回归）；
GPU 为 opt-in、默认关闭、带熔断与 CPU 回退。**1.51x + 2% 像素可见差异** ——
是否默认开启取决于用户对那 2% 的接受度，这个判断应交给实测观感，而不是代码。
若要继续缩小差异，方向是核对 CPU 手写内核与官方 shader 的逐条语义（`waterwaves` /
`opacity` / `foliagesway`），那是另一个量级的活。

### 开关已解耦

原先 `sceneGpuAccel` 被 `&& betaSceneAnim === true` 双重门控（`client.js` / `index.js`
两处 + `src/client.js` 源），而 beta 场景动画已搁置 ⇒ **这个开关永远传不出
`gpuAccel=true`，是个空开关；更糟的是切换它只作废帧缓存、不产生任何效果**。
现已解耦为独立开关（UI 行不再要求 beta 开启，关闭 beta 也不再复位它），
`lib/client.js` 已重新构建，`verify` 全绿。

## 十五、其它加速手段分析（按证据强度排序）

已测成本结构（4K 静态帧）：效果链 17–79%、纹理解码最大单项（渲染器侧
`3486806915` 为 2218/4122ms）、非效果部分约 2800ms（@1920×1080，GPU 开启后仍在 CPU）、
PNG 编码 140–900ms。

| # | 手段 | 预期收益 | 依据 / 代价 |
|---|---|---|---|
| ① | **多线程并行** | **4–8x** | 24 逻辑核，当前全单线程。效果内核、解码、blit 都按行/按纹理独立，天然可并行。**覆盖面比 GPU 广**（GPU 只接管效果链，解码+blit 仍在 CPU）。代价：线程池 + SharedArrayBuffer，小 pass 需阈值防调度开销；受内存带宽限制拿不到 24x |
| ② | **跨实例纹理解码缓存** | 中 | 渲染器 `textureCache` 是**实例内**的（换壁纸即失效）；合成路径只有单次调用内缓存。库扫描时重复解码可观。代价：内存（8K 贴图解码后单张 232MB） |
| ③ | **空闲预热 + 持久帧缓存** | 消除等待 | **不改渲染速度，改"谁在等"**。帧缓存已有，缺的是扫描后/GUI 空闲时后台逐张预热。与任何渲染优化正交，是把 10s 移出交互路径的唯一手段 |
| ④ | PNG 编码优化 | 小 | 140–900ms/帧（占可见总计 4–19%）。降 zlib level 或照片类帧改 JPEG |
| ⑤ | 进程级并行 | 中（预热场景） | worker 已是独立进程；库预热时可多场景并发。与 ① 互补（① 是单场景内，⑤ 是多场景间） |
| ⑥ | Dawn/Vulkan 后端 | 未知 | `gpu-dawn/backend.js` 与 gpu-gl 一样是死代码。理论更快（真 Vulkan 而非 ANGLE 转译），但依赖更重、风险高于把现有 GL 路径做扎实 |
| ⑦ | 剔除不可见工作 | 已证偏低 | 离屏层剔除在解码缓存之后只剩 200–300ms 空间；`blurprecise` 早已跳过 |
| ⑧ | 对齐官方语义 | 画质而非速度 | 若 GPU 跑官方 shader 观感更好，正确动作是**逐条修 CPU 手写内核**，最终可能让多数效果不再需要手写实现 |

**排序建议**：目标"用户等待"→ ③；目标"渲染更快"→ ① > ② > ④；
目标"画质"→ ⑧（GPU 开关正是这条路的验证工具）。

## 十六、多线程并行：加速曲线实测（含"不占满核心"的边界）

先量加速曲线再决定是否动线程模型。负载取"逐像素双线性重采样 + alpha 合成"
（多层合成 blit 的形状，内存带宽敏感型，与效果内核同族）：
源 4096×4096 → 目标 3840×2160，SharedArrayBuffer 共享，仅行区间走 postMessage。
`scripts/tmp-parallel-bench.mjs`。

| workers | 耗时 | 加速 | 与单线程逐位一致 |
|---|---|---|---|
| 1 | 263ms | 1.00x | — |
| 2 | 152ms | 1.73x | ✓ |
| 4 | 100ms | 2.62x | ✓ |
| 6 | 93ms | 2.83x | ✓ |
| **8** | **90ms** | **2.91x** | ✓ |
| 12 | 103ms | 2.54x | ✓ |
| 16 | 104ms | 2.52x | ✓ |
| 24 | 143ms | 1.84x | ✓ |

### 三个结论

**① 天花板是 ~2.9x，不是我先前估的 4–8x。** 8 worker 后开始**回退**，
24 worker 反而只有 1.84x —— 典型的**内存带宽饱和**。行切分不改内存访问总量，
所以上限由带宽而非核数决定。**这条要写进预期管理。**

**② 逐位一致在每个 worker 数下都成立。** 行切分是输出保持的，这让并行可以放心做。

**③ 你担心的"占满核心"与性能最优是同一个方向 —— 不是取舍。**
最优点是 **8/24 ≈ 33% 的核心**。少用核心不但更友好，而且**更快**。
低端 4 核机上按同比例取 2 个 worker（留 2 核给 GUI），仍能拿到约 1.7x。

### 因此的 worker 上限策略

```
workers = clamp(2, floor(逻辑核数 × 0.34), 8)
  · 24 核 → 8      （实测最优点）
  · 8 核  → 2
  · 4 核  → 2      （强留 2 核给系统/GUI）
像素数 < 阈值 (约 1 Mpx) 时**不并行** —— 线程派发 ~1-3ms 会吃掉小 pass 的收益。
另留配置项允许用户显式调低 (低端机/笔记本电池模式)。
```

**尚未实施的部分**：线程池本体与效果链集成。加速曲线与一致性已验证，
但把池接进 `applyEffects` 需要处理（a）内核依赖 `this`（采样器/纹理缓存）如何在线程间界定，
（b）scratch 池是模块级单例、跨线程不共享，（c）`SharedArrayBuffer` 化纹理数据的内存代价。
这三条都是有明确解法的工程活，但改动面不小，应在下一轮单独做、单独验证。
**在完成之前不应合入。**

## 十七、并行池已建并验证，但**按纹理并行只有 1.34x**

### 做了什么

选**解码**而非效果内核作为并行的第一刀，因为它绕开了 §十六 列的三个拦路问题里的两个：
`decodeTexToRgba(bytes)` 是**纯函数**（不吃渲染器 `this`、不碰 scratch 池），纹理之间天然独立。

- `lib/we-renderer/parallel.js`：并行池 + **保守尺寸策略**
  `workers = clamp(2, floor(核数 × 0.34), 8)`（实测最优点），
  低于阈值（<2 项或 <512KB）不并行（派发 1–3ms 会吃掉小任务收益），
  `DSH_WE_NO_PARALLEL=1` 可强制串行（低端机/排障）。
- `lib/we-renderer/decode-worker.mjs`：解码 worker，RGBA 经 transfer list 零拷贝回传。
- `decodeTexToRgba` 从 `pkg-extract.js` 导出。

### 验证结果：一致性满分，加速不及预期

```
逻辑核 24    workerBudget=8（= 核数×0.34，上限 8）✓ 策略生效
同步 2015ms  →  并行 1509ms     加速 1.34x
逐字节一致: 是（65 张, 不一致 0, 缺失 0, 最大Δ 0）
```

**一致性满分**（最大Δ 0），但 **1.34x 远低于合成基准的 2.91x**。原因是
**Amdahl 定律在"项"这一级的硬上限**：

该场景 2015ms 里有 **1308ms 是单张 `鸟_00020`（7680×7920）**。按项并行时，这一项
不可再分，落在哪个 worker 哪个 worker 就要跑满 1308ms ⇒ **理论天花板
= 2015/1308 = 1.54x**，实测 1.34x 已经贴近这个上限。

**所以"按纹理并行"对真实场景是错的粒度** —— 只要有一张贴图占主导，加速就被它锁死。
要拿到 ~2.9x 必须做**解码内部的按行切分**（即 §十六 基准测的那种形状），
那是解码器改造，比加个池深得多。

### 尚未接线（且因此当前是未使用代码）

`tryCompositeSceneLayers` 是**同步函数**，而并行解码是异步的；改成异步会沿
`extractSceneMainImage` → `index.js:3106` 一路上溯。这是已定位、但本轮未做的改动。

因此 `parallel.js` / `decode-worker.mjs` **目前没有任何调用方**。
两个选择：**下一轮接线**（连同解码器按行并行一起做，才有意义），或**先撤掉**
—— 按本项目对死代码的一贯标准，不该以未接线状态合入。

## 十八、叠加优化的算术：**不相乘，而是加权调和**

"叠加多种优化"是对的方向，但收益**不是相乘**。设各阶段耗时 t_i、各自加速 s_i：

```
整体加速 = Σt_i / Σ(t_i / s_i)        ← 加权调和平均, 不是 Πs_i
```

推论（也是选路依据）：**优化一个已经变小的阶段收益趋近 0，且整体被"降得最少的那个
主导阶段"卡住。** 所以每做一步都要**重新看阶段排序**——瓶颈会移动。

### 以 `3486806915` @1920×1080 为例（实测值）

| 步骤 | 效果链 | 非效果(解码+blit+文本/粒子) | 合计 | 累计加速 |
|---|---|---|---|---|
| 基线 (CPU) | 3044ms | 2843ms | 5887ms | 1.00x |
| + GPU 效果 | **1093ms** | 2843ms | 3894ms | 1.51x |
| + 非效果按行并行 (2.91x) | 1093ms | **977ms** | 2070ms | **2.84x** |
| 若误以为"相乘" | — | — | — | ~~4.4x~~ ❌ |

**1.51x 与 2.91x 叠加得到的是 2.84x，不是 4.4x。** 这是本轮最该记住的一条：
叠加优化要在**阶段之间**分配精力，而不是把某一个阶段做到极致。

### 瓶颈已经移动了

做完 GPU 之后，**非效果阶段反而成了主导（73%）**——所以下一步该做的是并行，
不是继续打磨 GPU。而做完并行之后，新的主导会变成：

| 做完前两步后的 2070ms 构成 | 耗时 | 性质 |
|---|---|---|
| GPU 效果阶段 | 1093ms | **已不是计算主导，而是上传+回读的传输开销** |
| 非效果阶段 | 977ms | 继续并行收益递减（受内存带宽限制） |
| PNG 编码 + 落盘 | ~50–900ms | 受编码器限制 |

**新发现的优化点**：GPU 效果阶段的 1093ms 现在主要是**每个效果一次上传+readPixels
回读**（4K 单次约 13–24ms）。把同一对象的连续效果**在 GPU 内 FBO 乒乓链式执行**、
只回读一次，能把这个阶段再砍一大截 —— `runEffectChainOnGL` 正是为此而存在
（§十四 因它半成品而没接）。当时不接是对的（那时该阶段是计算主导，链式收益小）；
**现在数据支持接它了。**

### 各手段之间：互补、替代、还是包含

| 关系 | 例子 | 含义 |
|---|---|---|
| **互补（可叠加）** | 解码缓存 × 按行并行 | 缓存去掉重复项，并行切分剩下的；两者都作用于解码阶段的不同来源 |
| **替代（不要都做）** | GPU 效果 × CPU 效果并行 | 都只打效果阶段。GPU 路径根本不进 CPU 内核，做了并行也用不上 |
| **包含（做大的可省小的）** | 跨实例解码缓存 ⊃ 按行并行 | 解码结果长期留存后，重复视图不再需要并行解码 |
| **正交（真正独立）** | 空闲预热 × 任何渲染优化 | 预热减少"付几次"，并行减少"每次付多少" |

### 因此的路线

1. **空闲预热 + 持久帧缓存**（正交、零观感风险）—— 把等待移出交互路径。
   对 126 场景的库，这是唯一能同时改善"每一个壁纸"的手段。
2. **按行并行的解码器**（无损、基准已证 2.91x、只用 1/3 核心）—— 覆盖当前主导阶段。
3. **GPU FBO 链式效果**（现在才值得做）—— 砍传输开销，目标把 1093ms 压到数百 ms。
4. PNG 编码器调优（收尾的 4–19%）。

**预期叠加结果**：冷启动最坏场景 10.4s → 约 **2s**；
配合预热，用户实际感知 ≈ **0**（切换即命中缓存）。

## 十九、PNG 编码级别实测：杠杆比预期小，且是取舍

`encodePng` 用 filter 0（无自适应滤波）+ `deflateSync(level: 6)`。在同一份真实帧上
（1920×1080, raw 7.9MB）测各级别：

| level | 耗时 | 产物 | 速度 | 体积 |
|---|---|---|---|---|
| 1 | 19ms | 0.99MB | 2.47x | 1.23x |
| 3 | 22ms | 0.93MB | **2.14x** | 1.16x |
| 6 | 47ms | 0.80MB | 1.00x | 1.00x |
| 9 | 127ms | 0.79MB | **0.37x** | 0.98x |

**结论**：

- **level 9 毫无意义** —— 慢 2.7 倍只换来 2% 体积。
- **level 3 是拐点**：编码快 2.14x，体积只涨 16%。
- 但**绝对值很小**：1080p 省 25ms，4K 约省 100ms；对照 PNG 在用户可见总计里
  占 4–19%，换级别大约只省 **2–9%**。
- **并且有代价**：帧缓存文件大 16% ⇒ 同等磁盘上限下能缓存的帧数少 16%。
  对"缓存本身就是最大加速手段"的系统，这个交换未必划算。

**没有动这一行** —— 它是取舍不是净赢，应由你按"编码速度 vs 缓存容量"的优先级决定。

真正值得做的 PNG 优化不是级别而是**自适应滤波**（Paeth/Sub/Up）：照片类内容通常
能同时改善体积**和**速度（滤波后数据更可压缩，可用更快的 level 达到更小体积）。
`decodePngBuffer` 已支持 filter 0–4，所以解码侧无需改动。这是一次真正的编码器改动，
需要自己的验证，属于独立一轮的活。

## 二十、该做什么：目标、取舍与优先级

### 先纠正目标本身

整轮测量指向一个之前没被说清的结论：**用户要的不是"渲染快"，而是"切换时立刻看到画面"。**

初始抱怨的三件事——"更新后缓存全失效逐个重载"、"陷入很长时间的等待依旧没有效果"、
"10 秒黑屏"——**没有一件是"渲染不够快"，全部是"等待落在交互路径上"**。
0.7.3 之所以被怀念，也不是因为它渲染快（实测它的回退路径 688ms–12.3s，一点不便宜），
而是因为**产物被缓存下来、切换即命中**。

所以"让单帧渲染从 10s 变 2s"和"让用户看不到等待"是**两种不同的货币**，
而后者才是原始诉求。

### 目标（可度量）

| 目标 | 指标 | 现状 | 备注 |
|---|---|---|---|
| **G1 感知** | 切换壁纸 → 首帧可见 | 命中即瞬时；未命中黑屏 2.3–10.4s | **主目标** |
| **G2 冷渲染** | 最坏场景冷渲染 | 10.4s | 目标 < 4s |
| **G3 预热** | 全库 126 场景预热 | 不存在此机制 | 空闲完成、不占满核心 |
| **G4 保真** | GPU vs CPU 输出差异 | 2.04% 像素 >32/255 | 待决策 |
| **G5 健壮** | 无 GPU/驱动时 | 已熔断回退，功能不退化 | ✅ 已达成 |

### 该做（按用户价值排序，非按技术含量）

**① 空闲预热 + 持久帧缓存** —— 唯一直接命中 G1 的手段
不改渲染语义、无保真风险；把 2–10s 从交互路径移到空闲期。
需处理：队列取消/优先级、磁盘上限、核心占用（复用 §十六 的 1/3 核策略）。
前提是 G2 别太慢（126 张 × 平均 3s ≈ 6 分钟空闲时间，可接受）。

**② 按行并行的解码器** —— 命中 G2
基准实测 2.91x、逐位一致、只用 1/3 核。**必须切在"行"而非"项"**——
§十七 证明了按项并行只有 1.34x（单张 8K 贴图锁死整条流水线）。

**③ GPU FBO 链式效果** —— 命中 G2（第二步之后才值得）
做完 ② 之后效果阶段变成**传输主导**（1093ms 里主要是每效果一次上传+回读），
链式执行只回读一次能再砍一截。依赖 G4 的决策。

### 不该做（附理由，避免重复踩）

| 不做 | 理由 |
|---|---|
| 纹理降采样 | 用户已否决（破坏观感），且实测效果耗时与输出分辨率无关 |
| 降低输出分辨率 | 同上，实测无效 |
| 内核微优化 | 实测无空间（展开 4 通道 0 收益，采样已达裸吞吐） |
| PNG 级别调整 | 仅 2–9%，且有 16% 缓存容量代价；自适应滤波才值得但属收尾 |
| **接入已建好的 `parallel.js`（按项并行）** | 只有 1.34x，配不上接线要付的异步上溯成本。**建议撤掉**，按行重做 |
| Dawn/Vulkan | 收益未知、依赖重；现有 GL 路径尚未榨干，不该开第二条战线 |

### 一个优先级倒置（值得单独说）

按"技术含量"排会把并行排在预热前面；按"用户价值"排必须反过来：

- 预热**直接消除**用户唯一的抱怨，且不需要正确性验证；
- 并行的 2.91x 作用在**冷渲染**上——而预热生效后，冷渲染基本只发生在一次性的
  预热过程里，用户几乎看不到；
- 换句话说：**并行让预热更快，预热让并行变得不那么重要。**

所以正确顺序是 **① 预热 → ② 并行**：先把用户感知拉到 G1，再用并行把一次性成本压下去。
反过来做，会在一个用户感知不到的地方投入最多工程量。

### 需要你拍板的三个决策

- **D1 · 接受 GPU 的 2% 像素差异吗？** 决定 GPU 是"可默认开启"还是"永远 opt-in"。
  接受 ⇒ G2 的一半收益立刻落地；不接受 ⇒ 先做"CPU 内核对齐官方 shader"（另一个量级）。
- **D2 · G1 还是 G2 优先？** 决定先做 ① 还是 ②。我的建议是先 ①。
- **D3 · 缓存磁盘上限能放宽吗？** 预热 126 张 4K 帧约需数百 MB ~ 2GB。

### 决策已定（2026-09-20）

- **D1 · 接受 GPU 的 2% 像素差异**，但**留档为后续处理项**（对齐 CPU 手写内核与官方
  shader 的语义）。⇒ GPU 可进入默认路径，G2 的一半收益落地。
- **D2 · G1 优先**（用户感知优先于冷渲染吞吐）。
- **D3 · "预热全库 4K 帧"不现实**（126 × 2–17MB ≈ 0.5–2GB，且占大量 CPU）。
  ⇒ 改为**排队预热机制 + 预热开关**，范围受控。

### 排队预热设计（待实施）

**核心认识：G1 不需要"预热全部"，只需要"预热接下来会用到的那几张"。**
用户实际是在少数几张壁纸之间来回切，所以按使用模式排序即可，无需覆盖全库。

**1 · 范围：有界环，不是全库**

| 优先级 | 内容 | 默认 |
|---|---|---|
| P0 | 当前选中场景（帧缺失） | 走既有按需路径，不算预热 |
| P1 | 相邻项（上/下一张）+ MRU 历史前 N 张 | ✅ 默认预热这些（N 默认 6） |
| P2 | 全库其余 | ❌ 默认**不**预热；仅在用户显式选择"预热更多"时 |

队列**持久化**（重启后续跑），并且只预热**真实渲染产物**（`key.png/jpg`）——
**绝不把 `.fb.` 回退帧当预热结果写盘**（这正是此前"interim 被当成本体"的坑）。

**2 · 空闲门控**

仅在以下条件全部满足时出队：无渲染在飞、用户无操作 ≥30s、可选"仅交流电"。
任何用户交互**暂停**预热；切换壁纸时该场景**提升到队首**（或直接交给按需路径）。

**3 · 并发 = 1** ← 这是"不卡顿"的关键决定

一次只跑一个预热渲染。理由：单次渲染本身已是一个独立 worker 进程；用户正在交互；
且按行并行落地后单次渲染会占用约 1/3 核心。**并发 >1 会成倍推高核心占用，
正是要避免的"低端机全核占满"。**

**4 · 开关**

- UI："空闲预热"开关，**默认关闭**（会写盘、烧 CPU，需用户知情选择）。
- "预热范围"：仅常用几张（默认）/ 更多。
- 诊断逃生门：`DSH_WE_NO_PREWARM=1` 强制关闭。

**5 · 缓存与预算**

预热写入与按需路径**完全相同**的缓存键 ⇒ 预热帧是合法命中，不是特权产物。
总磁盘占用沿用既有 LRU 上限；到顶时停止出队或按 LRU 淘汰。
预热前**先查缓存键**，命中则跳过（避免重复渲染）。

**6 · 可观测**

计数：已预热 / 跳过（已命中）/ 失败 / 队列长度。沿用 `gpu-diag.log` 的异步落盘模式。

**7 · 与后续工作的关系**

- 与 **② 按行并行**互补：并行减少"每次付多少"，预热减少"付几次"。
  且并发=1 的设计使两者不冲突——并行的收益是让队列更快排空。
- 预热完成后，G1 对"常用那几张"即达成；G2 的优化只影响**首次预热耗时**与
  缓存未命中场景，优先级低于 G1——这与 D2 的结论一致。

**8 · 不建议现在写代码**

排队预热需要同时改：队列模块（新）、设置项（`client.js` + `index.js` + 重新构建）、
以及 `index.js` 里帧产出的接入点。**分三次改动、只做其中一次会留下未接线代码**
（正是 §十七 里 `parallel.js` 的教训）。应作为完整一轮来做，配一个能验证
"预热帧与按需帧同键同内容"的护栏。

## 二十一、v0.7.3 的"静默回退"到底是什么（代码取证）

对比 `8a0d1d8`（0.7.3）与 HEAD 的 `${BASE}/scene-frame` 路由，四处关键差异：

| 维度 | **0.7.3 (`8a0d1d8`)** | HEAD |
|---|---|---|
| 缓存键 | `'sf33_' + b64(abs) + '_' + mtime` —— **无 gpu 标志** | `PIPELINE_VERSION + '_' + gpuFlag + '_' + b64 + '_' + mtime` |
| 回退产物落盘位置 | **与真实渲染同一个 `pngPath`/`jpgPath`** | 独立 `.fb.png` / `.fb.jpg` |
| 尺寸上限 | **无**（`capFallbackFrame`/`FALLBACK_MAX_WIDTH` 都不存在） | 3840 宽 |
| 取消 | **无**（`renderSceneFrameInWorker(src, fw, fh, 2.5)` 不传 `signal`） | 等待者计数 + AbortController |

**所以 0.7.3 的"静默"是名副其实的**：回退产物写进与真实渲染**同一个文件**，事后
**无法从文件名或缓存键区分**——它就此变成正式帧，永久命中。这正是你记忆里
"产物直接当正式帧缓存下来"的机制。而 `sf33_` 键里的 `mtime` 才是刷新依据。

回退 trigger 两版一致：渲染失败（`!result.ok`）**或**空帧门禁
（`result.diff < result.checked * 0.0005`）。回退内容两版都是
`extractSceneMainImage`（composite-or-single-texture），**且 composite 函数体
在 0.7.3→HEAD 之间没有改动**（`git diff` 的 hunk 全部落在 668/996/1004/1516-1528，
不含 composite 所在的 ~1160-1350 区间）。

### ⚠️ 修正：不要把"别人觉得不错"当成"你也觉得不错"

上一版这里写过一句错的推断：既然 0.7.3 的 composite 与现在同一份代码，那
"28.7% 区块均差 >40"就"是你 0.7.3 时期实际看到的画面，而你当时觉得还不错"。

**这个推断建立在错误的信息归属上。** 用户已明确澄清：

- **"还是很不错"来自作者/社区的报告反馈**——那是别人对自己**不同壁纸库**的判断；
- **用户自己的实测结论是"挺糟糕的"**；
- 两者不可互相替代：**不同的人选完全不同的壁纸**，谁对谁错无法一般化判定。

**因此结论不是"0.7.3 其实够用"，而是相反 —— 这正是必须做成开关的理由：**

> 用户选择"开关"而不是更省事的"整体回退"，恰恰因为**好坏的判断依人依库而异**。
> 开关让每个人按自己的库和眼力决定；回退则是替所有人做了同一个判断。

这条也适用于本文件里其它"用户观感"类的引用：**署名不清时一律标注来源**，
不要把转述、社区反馈与用户实测混为一谈。

### 28.7% 差异的正确读法

既然 0.7.3 与现在的 composite 是同一份代码，那个差异**客观存在且与版本无关**：
它是"主纹理合成"与"完整渲染器"两套实现之间的差距，不是某个版本的回归。

它包含**合法差异**（粒子、效果绘制的图层如窗户）与**疑似缺陷**（`attachment`
锚点未处理导致的角色错位）。前者是设计取舍，后者是真问题 —— 而 ① 要修的正是后者。


### 复刻 0.7.3 时必须做的一个偏离

0.7.3 的"无尺寸上限"正是上游 issue #86 的成因（8192×4680 / 解码 146MB，启动卡顿与
显存占用）。**忠实复刻会把那个已知缺陷一起带回来。** 建议：模式取 0.7.3 的
*产物语义*（同一份 composite 逻辑 + 一等公民缓存），但**保留 3840 限幅**
（0.7.4 引入的、有明确理由的修正）。

### 待办（用户已决定"两个都做"）

1. **修 composite 的 `attachment`/puppet 锚点处理** —— `pkg-extract.js` 目前零处理，
   而本地库 **7/7 个走 composite 的场景全都含 puppet**。先做对照实验坐实：
   在零 puppet 的多层场景（`2934788040` / `3470764447` / `3660962877` /
   `3690417937` / `3774904326`）上重复分块比较，若差异显著变小即证实局部热点
   源于 puppet 错位。**注意**：这 5 个场景当前走的是单贴图路径，需先查清
   它们为何没进 composite（`PATH_PENALTY_RE` / 层数 / 质量门）。
2. **加 `sceneFrameSource: 'render' | 'maintexture'` 选项**：缓存键加 source 位
   （两模式互不命中、切换不作废对方）；主纹理产物写成一等公民（不用 `.fb.`）；
   提取失败或质量门拒收时**回退真实渲染，绝不返回空**；UI 文案明确标注
   "回到 0.7.3 画面 / 不含角色骨骼合成与效果"。

### ① 的前置调查已完成：对照实验**在本地做不了**

新增诊断出口 `compositeDiagInfo()`（`DSH_WE_DIAG_COMPOSITE=1`，库内不 console）。
本地 16 场景实测"未走 composite 的原因"：

| 场景 | 结果 | 未合成原因 |
|---|---|---|
| 2934788040 | 单贴图 | **quality-gate** `grayRatio 0.923` |

| 3660962877 | 单贴图 | **few-layers** 1 层可解码 / 2 候选 |

| 3486806915 / 3554161528 / 3655429099 | composite | —（均含 puppet） |

**两个结论：**

**A. 本地库不存在"零 puppet 且走 composite"的场景 ⇒ 我上轮提的对照实验没有对照组。**
不能靠它来证实或推翻 puppet 错位的推断。要如实承认这一点，而不是硬找一个近似场景
充当对照。

**B. 这个选项在用户库上的真实覆盖面比预想窄。** composite 分支的入口条件相当严：
本地只有 **7/16** 进入 composite（且全部含 puppet），其余走**单贴图**，
另有质量门/候选不足的拒收。所以 `maintexture` 模式在这套库上的实际形态是：
7 张合成帧（带未验证的 puppet 风险）+ ~8 张单贴图 + 至少 1 张（`3640755971`）
**完全没有主纹理产物** ⇒ 必须回退真实渲染。

### ① 改用不依赖图像的验证方法

不需要看图的替代方案：**做数值对比**。`3486806915` 有 6 个带 `attachment` 的对象；
渲染器的 `resolveTransform` 会叠加 `_attachmentOffset`（骨骼锚点矩阵），而
composite 走的父链累积**不含**这一项。分别取出两者对同一对象算出的 origin，
差值即"错位像素数"。

- 差值小（几 px）⇒ 风险可忽略，① 可以不做；
- 差值大（几十 px 以上）⇒ 角色部件确实会明显错位，① 必须做。

这条路只需要数值，不需要目视，是目前唯一可行的判定手段。

### ① 判定结论：**必须修**（锚点缺失导致角色部件错位 ~511px）

判定脚本 `scripts/verify-composite-anchor.mjs`。**方法经过两次失败才定下来**，过程本身
值得记录：

**失败尝试 1 —— 跨场景对照**：想拿"零 puppet 且走 composite"的场景作对照。
实测发现本地库**不存在**这种场景（composite 分支只对 7/16 场景触发，且全部含 puppet）→ 对照组不可得。

**失败尝试 2 —— 两个函数相减**：直接拿渲染器 `resolveTransform` 减去 composite 的
`resolveObjectTransform`。结果**不带 attachment 的 142 个对象差值反而更大**
（中位 1057px、最大 3997px），而最大 2202.9px 恰等于 `√(1920²+1080²)` ——
那是两边**根默认值不同**（composite 用投影中心，渲染器用 `[0,0,0]`）造成的系统性偏差，
把锚点项完全盖住了。**两套独立实现的相减量不出单个因素的贡献。**

**成功方法 —— 打桩法**：把渲染器的 `_attachmentOffset` 临时替换为返回 `[0,0]`，
再算一次 `resolveTransform`。两次之差**恰好**是锚点项，不带 attachment 的对象天然为 0。

**结果（`3486806915`, 3840×2160, t=2.5s）**：

| 组 | n | 中位 | 最大 |
|---|---|---|---|
| 带 `attachment` | 6 | **511px** | **584px** |
| 对照（不带） | 142 | **0px** | 584px |

- 对照中位 **0.0px**，非零 25/142，且**其中无附着祖先的 = 0 个** ⇒ 方法自洽。
  （非零的那些是"自身不带 attachment 但链上有附着祖先"的对象 —— `resolveTransform`
  对链上每一环都叠加锚点项，这是**正确行为**，不是噪声。）
- 带 attachment 的对象错位 **145.6–584.0px**：`五官`/`头发` 584px、
  `头`/`右垂发` 511px、`右臂` 427px。画布宽 3840px ⇒ **错位达画面宽度的 13–15%**。

**结论：`maintexture` 模式下角色部件会明显错位，① 必须先修。**
这不是"边缘可见"，是"整张脸/头发挪了大半个身位"。

该脚本在 ① 修完后转为**回归护栏**：断言所有带 attachment 的对象错位为 0。

### ① 的决定性发现：**composite 把 puppet 图集当普通图层贴了**（7/7）

在动手修锚点之前先补了一个更根本的检查：`tryCompositeSceneLayers` 的图层过滤
**没有排除 puppet 对象**，而 puppet 的材质贴图是**图集**（UV 蒙皮用的部件网格图）。
把图集当普通 quad 贴上去，画面会出现"部件网格"。

诊断出口现在会报告每个 composite 里有多少层来自 puppet：

| 场景 | 层数 | **其中 puppet 图集层** |
|---|---|---|
| 3461168300 | 5 | **2** |
| 3486806915 | 43 | **8** |
| 3554161528 | 8 | **1** |
| 3582367840 | 13 | **1** |
| 3629379075 | 34 | **5** |
| 3641860575 | 11 | **6** |
| 3655429099 | 30 | **3** |

**7/7 —— 每一个走 composite 的场景都含 puppet 图集层。**

这同时解释了 §二十一 里那个"28.7% 区块均差 >40、局部热点在 23–30% 宽 / 35–48% 高"
的分块比较结果：热点很可能就是被整张贴上去的图集。

**它也给了用户"0.7.3 挺糟糕的"一个具体机制** —— 那不是主观差异，是这个渲染缺陷。

### ⇒ 锚点修复**不够**，① 的做法必须改

把锚点补上，图集问题依然在。要让 composite 在这些场景上faithful，需要实现
**puppet 网格 + UV 蒙皮渲染** —— 那等于在 `pkg-extract.js` 里再写一个渲染器，
与本项目的收益完全不成比例。

**因此 ① 的结论修订为：不修 composite 的 puppet 路径；改为在 composite 场景上
让主纹理模式回退真实渲染。** 判定依据从"锚点错位 511px"升级为
"图集错位（结构性错误，非偏移量级）"。

### 主纹理模式的实际覆盖面（据此模式回退后的口径）

本地 16 场景：

| 类别 | 场景数 | 主纹理模式行为 |
|---|---|---|
| composite（含 puppet 图集） | **7** | **回退真实渲染** |
| 单贴图 | 8 | ✅ 生效（含 2 个 composite 被质量门拒收、改走单贴图的） |
| 全部提取失败（`3640755971`） | 1 | **回退真实渲染** |

**⇒ `maintexture` 模式在用户库上服务 8/16 场景，另 8 个回退。**
它排除掉的恰好是**多层角色壁纸**（7 个 composite 全是），也就是最"好看"的那一类。
这个代价必须在做 ② 之前让用户知情 —— 它显著改变了 ② 的价值判断。

**待用户确认的口径**（我建议的默认）：composite 场景一律回退真实渲染。
备选是"过滤掉 puppet 图集层后照常合成"（背景对、角色缺失）——
但让角色整个消失通常比慢一点更刺眼，我不建议。

### ② 已实施（sceneFrameSource 选项）

口径采用 `hasPuppet` 作为回退判据 —— 它**精确等价于"该场景不能用近似"**：
本地 16 场景实测 **7 个 composite 场景全为 `true`，8 个单贴图场景全为 `false`**，
另有 1 个（`3640755971`）整体提取失败。

| 改动 | 位置 |
|---|---|
| `sceneHasPuppet(scene, access)` + 两条返回路径附加 `hasPuppet` | `lib/pkg-extract.js` |
| 缓存键加 source 位 `gpuFlag + srcFlag + '_'` ⇒ 两模式互不命中 | `lib/index.js::ensureSceneFrame` |
| maintexture 分支：先提取 → `hasPuppet` 或无产物则**回退真实渲染** | 同上 |
| 提取结果复用给 `.fb.` 兜底（避免重复提取）；产物写**正式缓存路径**（一等公民，非 `.fb.`） | 同上 |
| `sceneFrameSource` 归一化 | `lib/index.js::sanitizeSettings` |
| 默认值 / 归一化 / 持久化 / UI 行（文案如实） | `src/client.js` + 重新 build |

**护栏**：`verify-prewarm.mjs` 新增 R19–R26 —— source 位隔离（R20）、

> 判定逻辑抽成纯函数 `isMainTextureUsable(frame)` 并导出，就是为了让 R24–R26 能

**主纹理模式的最终覆盖面**：本地库 **8/16 生效，8/16 回退真实渲染**。
回退的正是 7 个多层角色壁纸 + 1 个提取失败场景 —— 这是设计选择，不是缺陷：
对含 puppet 的场景，近似路径会贴出图集，那比慢一点更糟。

**残留**：`scripts/verify-composite-anchor.mjs` 保持为**诊断工具**（不接入 verify）——
① 的结论是"不修 puppet 路径"，锚点错位不再是否决项，故不转为断言。

## 二十二、延迟分析：瓶颈已从"产出"移到"送达"

用户反馈："节约的时间可感知了，但是还是没有快多少。" 这指向本文件从未测过的半边 ——
前面二十节全部在优化**帧怎么产出**，没有任何一节测过**帧怎么送到屏幕上**。

### 切换的完整延迟链

```
点击 → 设置 selection.url = frameUrl (src/client.js:1057)
     → 宿主 ensureSceneFrame: 缓存命中 = existsSync+statSync (毫秒级)
     → HTTP 流式返回帧文件
     → 浏览器下载 → 解码 → 上传 GPU → 合成
```

前两段（渲染 + 缓存查找）我已经优化过；**后两段从未测过**。

### 实测：帧体积是 11.8MB，且每次切换都要重下重解

磁盘上现成的帧缓存（`~/.dsh-wallpaper-engine/cache/frames`）：

```
10 个文件, 118.2 MB, 平均 11.82 MB/张, 最大 22.8MB, 全部 3840x2160 PNG
```

而 `${BASE}/scene-frame` 路由设的是 **`Cache-Control: no-store`**
⇒ 浏览器**每次切换都必须重新下载并重新解码**整张帧。

**这就是"可感知了但还是没快多少"的机制**：预热/主纹理模式只影响**首次生成**，
而用户日常做的是**来回切换**，每次都在付这 11.8MB 的传输 + 解码。

### JPEG 能把载荷缩到 1/5 – 1/14

在真实帧上实测（解码现成 PNG → 重编码）：

| 帧 | PNG | PNG 解码 | PNG 重编 | **JPEG q85** | JPEG q92 |
|---|---|---|---|---|---|
| 1 | **22.8MB** | 236ms | 699ms | 543ms / **3.35MB** | 648ms / 4.69MB |
| 2 | 16.4MB | 228ms | 714ms | 439ms / **1.19MB** | 383ms / 1.65MB |
| 3 | 7.5MB | 219ms | 403ms | 375ms / **1.24MB** | 406ms / 1.78MB |
| 4 | 7.1MB | 167ms | 347ms | 474ms / **2.22MB** | 580ms / 2.95MB |

- 体积 **1/5 – 1/14**，且 JPEG 编码**不比 PNG 慢**（22.8MB 那张：543ms vs 699ms）。
- **alpha 安全性已验**：抽样的 8 张帧全部 **0% 透明 / 0% 半透明**（`clearenabled`
  会填底色，画布整体不透明）⇒ JPEG 可用。**但 `clearenabled:false` 的场景可能产出透明帧**，
  故需**逐帧判定**：任何 alpha < 255 就回退 PNG。

### ⚠️ 修正：上面的"送达是瓶颈"归因**不成立**

用户直接观测到：**已缓存的帧切换几乎没有延迟**。这与上面"每次切换都要付 11.8MB
传输+解码"的结论直接冲突。

**我的推理错在哪**：`no-store` ⇒ 每次重新请求 ⇒ 慢，这是**推断**；而且我**从未验证
浏览器真的重新请求过**。"送达"这一段的实际代价从未被直接测量。**观测优先于推断，
所以这个归因撤回。**

正确的延迟模型是：

```
感知延迟 = P(未命中) × 产出耗时 + P(命中) × ≈0
```

既然命中几乎免费，**成本全在"未命中"** ⇒ 杠杆只有两个：**降低未命中率**、
**缩短产出耗时**。"送达"不是主项。

### 实测未命中率与容量（取代上面的推断）

缓存文件名里编码了场景路径（base64url 的 token **含 `_`**，按 `_` 切分会切坏，
必须用正则），还原后：

```
缓存键前缀: 全部是 sf35a_0_  （9 帧）
命中 9/16 场景: 2934788040 3461168300 3486806915 3554161528 3629379075
                3640755971 3641860575 3655429099 3669681034
未命中 7/16:    2820944015 2820948097 3470764447 3582367840
                3660962877 3690417937 3774904326
```

- `FRAME_CACHE_MAX_BYTES = 2GB`，实际占用 **118MB** ⇒ **没有淘汰压力**。
  126 场景 × 11.8MB ≈ 1.5GB，也仍在 2GB 之内。
- ⇒ **未命中是"从未渲染过"（冷），不是"被淘汰"（颠簸）。**
  我原先怀疑的缓存颠簸是错的。

### 本轮真正找到的问题：**我自己的改动作废了用户的缓存**

那 9 帧的前缀全是 `sf35a_0_` —— **旧键格式**。而我在 ② 里把键改成了
`PIPELINE_VERSION + gpuFlag + srcFlag + '_'`，新代码产出 `sf35a_0r_`。

**⇒ 我给默认模式也加了一位，等于把用户已缓存的 9 帧全部作废** ——
这正是用户最初回退 0.7.3 的头号原因（"更新后原本的缓存全部失效需要逐个点击重新加载"）。
**我复现了自己正在修的那个 bug。**

**已修**：默认模式（`render`）**沿用旧键格式**，只在**非默认**模式追加后缀：

```
render      : sf<ver>_<gpu>_<b64>_<mtime>      ← 与既有缓存一致, 继续命中
maintexture : sf<ver>_<gpu>m_<b64>_<mtime>     ← 独立命名空间, 两模式互不污染
```

护栏 R20 已改为断言这条**兼容性**（"默认模式沿用旧格式"），而不只是断言"有位"。

### 撤回 JPEG 建议

上面把 JPEG 的收益归结为"传输延迟"——既然命中切换几乎无延迟，**这个收益不存在**。
容量上也不紧张（2GB / 11.8MB ≈ 170 帧 > 126 场景），所以"提高有效容量"的理由同样不成立。

**⇒ JPEG 出帧作为延迟优化不值得做**，除非你确有别的诉求（磁盘占用）。
有损压缩还要付观感代价，性价比不成立，我不再推荐。

## 二十六、亚托莉的根因：`decodePngPayload` 的字节下标 vs 像素步进

用户更正了描述："沿 x 轴压缩**到 75%** 左右到左侧，右侧透明"。实测完全吻合：

```
按 5% 宽度分段的不透明像素占比:
  100100100100100100100100100100100100100100100  0  0  0  0  0
  └────────── 0–75% 全部不透明 ──────────┘ └ 75–100% 全透明 ┘
```

### 关键对照：源数据没问题，共用的解码器也没问题

| 解码器 | 结果 |
|---|---|
| 源内嵌 PNG | 7680×4320, colorType=2 (**纯 RGB，无 alpha**), IHDR 合法 |
| **`decodePngBuffer`**（渲染器那份） | **100% 的列都有内容, 全部不透明** ✅ |
| **`decodePngPayload`**（pkg-extract 私有, `capFallbackFrame` 用的） | 只有 **75%** 的列有内容 ❌ |

**⇒ 缺陷在 `decodePngPayload` 本身**，不是源数据、也不是共享解码器。

### 根因（一行代码）

```js
for (let x = 0; x < w * channels; x++) {   // 遍历**源字节**
  ...
  rgba[y * w * 4 + x] = v;                 // ← 却把 x 直接当**目标字节下标**
}
```

对 **RGBA（channels=4）** 恰好等价（`x` 与 `px*4+ch` 恒等），所以一直没暴露。
对 **RGB（channels=3）** 则是把 3 字节/像素**紧密排列**进 4 字节/像素的缓冲区：

- 每行只填满前 `3w/4w = **75%**` 的字节，后 25% 保持 0 ⇒ **右侧整条透明**；
- 每个像素的 alpha 槽被"下一个像素的 R"覆盖 ⇒ 大部分像素看起来不透明但**通道整体错位**
  ⇒ 颜色发灰（实测均值 rgb(182,182,182)、通道极差仅 25.3）；
- 滤波器 `a`/`pr`/`pc` 也用了同一套错位下标，误差逐像素累积。

**一处 bug 同时解释了两个症状**（75% 宽度 + 黑白化）。

### 修复与验证

改为按像素步进 4 字节写入，滤波预测子同步改为 `d-4` / `d-w*4` / `d-w*4-4`；
RGB 源无 alpha 通道，显式补 `255`（原实现从不写 alpha 槽）。

| | 列覆盖 | 均值 | 通道极差 |
|---|---|---|---|
| 修前 | 75% 有内容, 右侧 25% 透明 | rgb(182,182,182) | 25.3 |
| **修后** | **20/20 段全部 100%** | rgb(198,186,162) | **50.3** |

RGBA（channels=4）路径**逐位不变**（新写法在 channels=4 时与旧写法恒等），
故既有帧产物不受影响。

### "花（静态）"黑屏的修复：压缩率判据

`isMainTextureUsable` 新增**近乎纯色/黑屏**判据。用**纯数学**定阈值 ——
本地库 16 个主纹理产物的**字节/像素**分布：

| 场景 | 字节/像素 |
|---|---|
| **`2934788040` 花（静态）**（实际整屏黑） | **0.0063** |
| 次小（`3660962877`） | 0.1776 |
| 最大（`3669681034`） | 2.1037 |

阈值取 **0.05**：命中 1 个，距最近正常值 **28 倍**余量。零解码成本。

**为什么不改用上游质量门**：那条门存在**无门分支**（JPEG 直通不检查；超大 PNG 的
`pngQuality` 返回 null 时被 `q &&` 短路），而兜底路径**刻意**选择"验不了就接受"
（有画面优于没画面，代码注释明说）。主纹理模式是**主产物**，需要相反的保守策略 ——
所以给它**自己的**判据，不依赖上游的隐含保证。

**实测结果**：`2934788040` → 判为不可用 → **回退真实渲染**（黑屏消除）；
`3669681034` → 解码修正后可采用；两个 puppet 场景仍按 puppet 判据回退。

**护栏**：R31（bpp 0.0063 ⇒ 不可用）、R32（次小真实值 0.1776 通过、0.04 拒收 ⇒
阈值有余量），与 R24–R26 一并接入 `npm run verify`（全绿）。

> R24 的夹具在本轮**必须改**：它原用 `Buffer.from([1])`（bpp≈0.0002），
> 加入压缩率判据后会被**正确地**判为不可用。**夹具失真会被误读成回归** ——
> 所以夹具也要按真实量级构造。

### 解码器的逐像素一致护栏（新增脚本）

`scripts/verify-png-decode.mjs`（已接入 `npm run verify`）：用**合成 PNG**（不依赖壁纸库）
断言 `decodePngPayload` 与渲染器那份 `decodePngBuffer` **逐像素一致**。

| 检查 | 内容 |
|---|---|
| R1 | RGB(3 通道) 逐像素一致 + alpha 补 255 |
| R2 | RGB 解码后**每一列都有内容**（缺陷症状：右侧 25% 整条透明） |
| R3 | RGBA(4 通道) 不得回归 |
| R4 | 滤波 1(Sub)/2(Up)/3(Average)/4(Paeth) 全覆盖（修复改动了 a/pr/pc 三条索引） |
| R5 | **负控制**：复现旧的"字节下标"写入，验证它必然留下右侧空列 |

R5 实测：旧写法空列 **10/40 = 25%**，与用户观察到的"压缩到 75%"完全一致 ——
**断言不是空转**，且我对机制的解释可被独立复现。

为何用合成小图而非真实的 33.2Mpx 场景：**该缺陷只与 channels 有关、与尺寸无关**
（`x` 与 `px*4+ch` 在 channels=4 时恒等，在 channels=3 时恒差），小图即可完整覆盖，
且护栏不依赖壁纸库、可在任何机器上跑。

### 关于任务③（质量门短路）的处置

③ 要求"`q === null` 不得放行"。**未改共享质量门**，理由：
兜底路径**刻意**选择"验不了就接受"（代码注释明说"有画面优于没画面"），
改它会把兜底路径的既有语义一起改掉。

| 交付（PNG 写出） | 159ms | 3.5% |

对象级：`鸟_00020` 1883ms（43.4%，6 个实例）+ `栏杆` 959ms（22.1%）= **65.5%**。

GPU 只能加速效果链（1027ms/24%），**碰不到解码**。所以"开了 GPU 加速还是不够快"
的原因不是 GPU 不够强，而是剩下的大头（52%）根本不在 GPU 的管辖范围内。

### 发现：解码了整张图集，却只用其中一帧

`鸟_00020` 的 TEX 带 `isAnimatedGif` 与 TEXS 帧表：

| 项 | 值 |
|---|---|
| 图集尺寸 | 7680×7920 = **60.8 Mpx** |
| 动画帧 | 56 帧，帧尺寸 **1920×720** |
| 单帧占图集 | **2.27%** |
| 整图解码 | ~1308ms（243MB RGBA） |
| 实际绘制尺寸 | 1920×720 … 5760×2160（= 图集面积的 2.3%–20.5%） |

渲染器流程是「整图解码 → 再裁出当前帧」，即**把 60.8Mpx 全部解成像素，只用了一帧**。
这与"纹理降采样"是完全不同的东西：降采样是**有损**（被放弃的路线），
而这里是**解码了根本用不到的数据**，去掉它不改变任何像素。

### 等价性证明（不是近似，是可证的恒等）

四条理由，缺一不可：

1. **绘制不读图集尺寸。** 该纹理全部 6 个实例的模型都带显式
   `o.size = "1920.00000 720.00000"`（正好等于帧尺寸），缩放 1.0–3.0 均匀 ⇒
   `renderImage` 里 `if (size[0]===0||size[1]===0) size = [tex.width, tex.height]`
   这一兜底**永不触发**。所以返回「帧尺寸纹理」与返回「图集纹理+裁剪」在
   尺寸解析上完全等价。
2. **帧矩形同源。** 两条路径（加载时只解码该帧 / 加载整图后裁剪）都调用
   `textures.js::atlasFrameRect()`，帧索引、帧宽高、帧偏移全部来自同一个函数，
   不存在两套公式漂移的可能。
3. **块压缩天然可分。** DXT1/3/5 每个 4×4 块独立编解码，抽出一段块行/块列
   交给**同一个解码器**，结果必然相同（复用同一函数，非重写实现）。
4. **越界即回退。** 任何不能精确处理的矩形返回 `null`，调用方走整图解码 ——
   没有夹取、没有近似、没有"尽力而为"。

守卫脚本 `scripts/verify-atlas-frame-decode.mjs`（已挂入 `npm run verify`）
用**纯数学对照**证明，不依赖真实素材、不依赖目视：**43 项全部通过**。

| 检查 | 内容 |
|---|---|
| 正对照 ×15 | DXT1/DXT3/DXT5 × {单块, 块对齐, 非对齐+跨块, 右下角, 整图}：区域解码 == 整图裁剪，**逐字节** |
| 负对照 ×3 | 矩形错位 1px 必须**不**相等 —— 证明上面的比较有区分力，不是空转 |
| 回退 ×13 | 越界/负坐标/零面积/非压缩格式 → `null`（回退整图） |
| 帧选择 ×14 | `atlasFrameRect` 与原 `image.js` 内联公式逐字段相同（显式帧元数据 + 全兜底两种情形） |

### 实现（4 个文件）

| 文件 | 改动 |
|---|---|
| `lib/pkg-extract.js` | 新增 `decodeDxtRegion()`（抽块 → 复用 `decodeDxt*` → 裁回精确矩形）；`decodeTex(data, opts)` 接受 `opts.frameRect` |
| `lib/we-renderer/textures.js` | 新增 `atlasFrameRect()`（帧选择唯一事实来源）；`loadTexImage(raw, opts)` 支持按帧解码，且只在**确实走了区域路径**时才改变尺寸语义 |
| `lib/we-renderer/core.js` | `loadTexture/loadModelTexture` 透传 `opts`；**帧索引进入缓存键**（`texPath#idx`）；`_cacheTexture(cacheKey, …)` |
| `lib/we-renderer/image.js` | spritesheet 动画在**加载前**请求当前帧；裁剪块改用 `atlasFrameRect` |

**门控三层，任一不满足即退回原路径**：① 格式必须是 DXT1/3/5；
② 必须是 `isAnimatedGif`；③ 图集必须 ≥ 4 Mpx（`FRAME_DECODE_MIN_PIXELS`）。

**缓存键安全**：区域解码只写进 `texPath#idx` 这个键，`texPath` 本身的语义
**完全没变** —— 普通请求永远不会读到单帧纹理。帧索引必须进键，否则多帧渲染
会复用上一帧的纹理（这是本改动最容易引入的 bug）。

**缓存兼容性**：默认 `render` 模式的缓存键格式**未改动**，不触发用户最痛的
"全库缓存失效"。这是硬约束，已由 `verify-prewarm.mjs` R20 守卫。

**明确排除**：`swayimage` / `flag` / `retro` 三种着色器在裁剪**之前**使用整张
纹理，故这三个着色器保持整图加载语义不变（否则会改变它们看到的输入）。

### 作用域限制（必须如实说明）

- **不是全库收益。** 本地库只有 **1/16** 个场景存在 >4Mpx 的动画图集。
  对这类场景收益极大，对普通场景**收益为零**（门控直接不触发）。
- **同一场景内也只有部分对象受益。** 同一 4K 场景里 `背景` / `左大衣` /
  `栏杆`（其中之一）的绘制面积达到图集的 **100%** ⇒ 它们**没有**可省的解码量。
  可省的只有 `鸟_00020` 这一类"图集远大于绘制尺寸"的对象。
- **投影（尚未实测）**：`鸟_00020` 解码 1308ms → 单帧约 30ms 量级，
  该场景渲染 4344ms 投影降至 **~3250ms** 上下。**这是投影，不是实测值。**

### 未解决的开放风险：多页图集

`鸟_00020` 的容器同时报告 `imageCount: 2`，而 56 帧 × 1920×720 = 77.4Mpx
**大于**单页 7680×7920 能容纳的 44 格（60.8Mpx）。也就是说，帧表中靠后的
若干帧其 `x/y` 可能落在 `mipmaps[0]` 之外。此时 `decodeDxtRegion` 返回 `null`
—— **行为上是安全的**（自动回退整图解码，不会画错），但**收益会缩水**，
且实际缩水多少取决于真实帧表布局，必须用真实素材实测，不能推测。

这也解释了守卫脚本里"情形 A、t=3.7 → y=9360 > 7920"的现象：那是**原公式
自身**的行为，两条路径一致地越界，而区域解码对越界一律回退 —— 一致性没有被破坏。

### 未做（需要用户明确同意才做）

- **按绘制尺寸解码**（把 60.8Mpx 解到 2.3%–20.5% 的面积）：**有损**，
  与"降采样"同类，**未获用户同意，不做**。
- **DXT 行并行解码**：块独立、已证明安全（行切分上限 2.91×，峰值在 8/24 核
  = 33%，24 worker 反而退化到 1.84×，受内存带宽限制）。属于通用收益，尚未接线。
- **`lib/we-renderer/parallel.js` / `decode-worker.mjs`**：已删除，
  理由见 §二十八 ⑤（实现的是被实测否定的"按纹理"轴）。

## 二十八、前提实测、一个真 bug 的定位、以及按帧解码的实测收益

### ① 前提实测（两条，真实素材，不是推断）

**①a 绘制尺寸 vs 纹理尺寸**（决定"按绘制尺寸解码"的收益上界）：

| 对象 | 纹理尺寸 | 实际绘制尺寸 | 占纹理面积 |
|---|---|---|---|
| `鸟_00020` | 7680×7920（60.8Mpx） | 1920×720 … 5760×2160 | **2.3%–20.5%** |
| `背景` / `左大衣` / `栏杆`(其一) | — | 与纹理 1:1 | **100%** |

→ 比值远小于 1 的只有 `鸟_00020` 这一类；`背景`/`左大衣`/`栏杆` 绘制面积
= 100%，**按绘制尺寸解码对它们零收益**。该方案本身**有损**，未获用户同意
—— **不做**。

**①b 主导纹理格式**（决定并行轴）：

四个主导纹理全部是 **DXT5、无内嵌 payload** ⇒ 块之间独立 ⇒ **可以切在块行**。
（若主导纹理是内嵌 JPEG/PNG，熵编码与 inflate 有顺序依赖，行切分才不适用。）

### ② 找到了一个真 bug：门控编辑没落盘，产出静默损坏

取证不靠读代码，靠计数器。`core.js` 中新增 `_atlasFrameReqs`（算出帧矩形并
发起请求）与 `_atlasFrameDecodes`（真正走到区域解码）。首次渲染实测：

```
frameReqs=1  frameDecodes=0        ← 请求发出了, 区域解码一次都没走成
```

根因：`loadTexImage` 中"逻辑尺寸裁剪 (DXT padding)"那一段**没有**被
`frameDecoded` 门控。于是区域解码返回的 1920×720 缓冲区被当作 padding，
按图集 7680×7920 重新解读并补零 —— **产出损坏纹理，且不报任何错**。

画布校验和（同场景、同 t、GPU 开）：

| | canvasSum |
|---|---|
| 修复前（损坏） | 55183268 |
| **修复后（正确）** | **51060945** |
| **关闭该优化（基准）** | **51060945** ← 与修复后完全相同 |

即修复后开/关产出**同一张图**。修复后 `frameReqs=1 frameDecodes=1`。

### ② 实测收益（交替重复，取中位数）

单次测量**不可用**：同一配置先后跑出 3877ms / 6056ms（相差 56%），远超效应量。
改为开/关**交替各 4 次**，只差一个环境变量 `DSH_WE_NO_ATLAS_FRAME=1`：

| | 渲染耗时（4 次） | 中位 | 解码（4 次） | 中位 |
|---|---|---|---|---|
| **开** | 3828, 3896, 3908, 3861 | **3878ms** | 1782, 1793, 1804, 1784 | **1788ms** |
| 关 | 5065, 5105, 5103, 5065 | **5084ms** | 2970, 2999, 3000, 2979 | **2989ms** |

**Δ渲染 = −1206ms（−23.7%）；Δ解码 = −1201ms（−40.2%）。**
同模式内 σ≈30ms，差值远超噪声。解码降幅与"60.8Mpx 全图解码约 1.2s"量级吻合。

### ③ 护栏（补上漏掉的那一层）

事故能溜过的原因很具体：守卫只测了 `decodeDxtRegion` 与 `atlasFrameRect`
两个纯函数，**没测 `loadTexImage` 的落盘门控**。已补：

| 检查 | 作用 |
|---|---|
| padding 裁剪被 `frameDecoded` 门控 | 本次事故的直接回归护栏 |
| 按帧解码后不再暴露 `frames` | 防止上层二次裁剪 |
| 尺寸不符时**抛错**而非静默损坏 | 运行时兜底 |
| 帧索引进入缓存键 | 防止多帧复用串帧 |
| 区域解码结果被计数核验 | 让"是否生效"可取证 |
| **负对照**：剥掉门控后判据必须变假 | 证明检查器非恒真 |

纯函数层 43 项 + 落盘门控 6 项，全部接入 `npm run verify`。
真实素材上的端到端等价性由两个诊断脚本承担（需要场景库，故不入 verify 链）：
`scripts/diagnose-atlas-frame.mjs`（区域解码 vs 整图裁剪，**逐位一致 ✓**）
与 `scripts/diagnose-scene-atlas-ab.mjs`（开/关整张画布校验和）。

### ④ 为什么达不到 <2500ms（如实说明，不虚报）

| 项 | 现状 | 可达下界 | 依据 |
|---|---|---|---|
| 解码 | 1793ms | ~620ms | 块行并行 2.91×（§十六实测；DXT 块独立） |
| 效果链 | 1131ms | 1131ms | GPU 已加速，无损手段已用尽 |

| **合计** | **3997ms** | **≈2828ms** | |

**即使用上已测得 2.91× 的块行并行，无损下界也只有 ≈2828ms，<2500ms 在
"只用无损手段"的前提下不可达。** 要突破必须动效果链或按绘制尺寸解码（有损），
后者需用户明确同意。

### ⑤ 为什么块行并行没有直接接线（结构性原因，非意愿问题）

`parallel.js` / `decode-worker.mjs` 实现的是**按纹理**并行 —— §十七 实测仅
**1.34×**，该轴被否定，**已删除**（连同只验证它的 `scripts/tmp-verify-parallel.mjs`）。

但删掉之后，块行并行也**不能**直接塞进现有路径，原因在代码结构：
`loadTexture` / `loadTexImage` 是**完全同步**的，被同步的渲染循环直接调用，
而 worker_threads 只能异步回收结果。要兑现那 2.91×，必须先加一次
**异步预解码 pass**：整帧渲染之前把该帧要用的纹理并行解好并塞进纹理缓存，
渲染时同步命中。这解释了它此前"写了却接不上"。

这是一个**独立工作单元**（预解码 pass + 缓存协同 + 泄漏/活锁防护 + 护栏），
本轮未做，列为下一步。

### 作用域（不夸大）

本轮收益是**场景特定**的：全库只有 **1/16** 个场景有 >4Mpx 动画图集。
这类场景 −23.7%（−1206ms）；其余场景该优化不触发，收益为 **0**。

## 二十九、块行并行预解码：前提实测、四个真 bug、以及 −524ms 的实测收益

### ① 前提实测：块行并行 **DXT 解码** 到底多快

**先纠正一处引用错误**：§十六 的 2.91× 是在
`scripts/tmp-parallel-bench.mjs` 上测的，而那个基准跑的是**双线性重采样 + alpha
合成**（内存带宽敏感型），**不是 DXT 解码**（整数位运算 + 243MB 写出）。加速比
不可外推，所以重新实测（`scripts/bench-dxt-parallel.mjs`，负载取真实规模
7680×7920 → 58MB 块流 → 232MB RGBA）：

| workers | 耗时 | 加速 | 逐位一致 |
|---|---|---|---|
| 1（单线程） | 1266ms | 1.00× | — |
| 2 | 734ms | 1.72× | ✓ |
| 4 | 422ms | 3.00× | ✓ |
| **8** | **324ms** | **3.91×** | ✓ |
| 12 | 294ms | 4.47× | ✓ |
| 24 | 321ms | 4.09× | ✓ |

单线程 48 Mpx/s —— 与渲染器里实测的 `鸟_00020` 全图解码 ~1.2s **互相印证**。
取 **8 worker（占 24 核的 33%）**：既是最优点附近，也满足"不在低端机占满多核"。

### ② 剩余解码花在哪里（决定值不值得做）

`scripts/inspect-decode-cost.mjs` 逐纹理实测（65 个 .tex 冷解码合计 2286ms）：

| 纹理 | 解码 | Mpx | 格式 |
|---|---|---|---|
| `鸟_00020`（动画图集，**已由 §二十七 处理**） | 1442ms | 60.83 | DXT5 |
| `栏杆` | 222ms | 7.09 | DXT5 |
| `背景` | 218ms | 8.29 | DXT5 |
| `左大衣` | 109ms | 3.29 | DXT5 |

前 5 名 88.4%；**DXT 占 96.7%**（非 DXT 仅 74ms，不可行切分，留给同步路径）。
⇒ **可并行的目标集合只有 ~526ms**，不是整块解码时间。

### ② 两个真 bug —— 都是实测抓出来的，不是读代码读出来的

**bug 1（更严重）：`texMip0Info` 用错尺寸，产出错误像素。**

第一版预解码跑完，解码确实降了，但**画布校验和变了**：
`46614380` ≠ 基准 `51060945`。我不靠推理，写了逐字节对比诊断，得到关键形态：
`背景` 逐字节一致，而 `栏杆`/`左大衣` **从第 4 行（= 第 2 个块行）开始不同**。

根因在 `lib/pkg-extract.js:739`：

```js
let { width, height, bytes } = mip0;   // ← 解码用 mip0 的**存储尺寸**
```

`decodeTex` 用 mip0 自身的尺寸解码，`loadTexImage` 之后再裁到逻辑尺寸。
而我的 `texMip0Info` 返回的是 `parsed.width/height`（逻辑尺寸）。二者不同时
（真实例：逻辑 3281 / 存储 3284）**块行跨距算错 → 第 0 块行看着完全正常，
其后每行漂移一个块**。这种错误目视极难发现，只有逐字节对照能抓到。

修法：`texMip0Info` 同时暴露 `storageWidth/storageHeight`（解码用）与
`width/height`（输出用），预解码完全复刻 `loadTexImage` 的裁剪语义。

**bug 2：同一容器被解压三遍。**

`core.js` 为算帧矩形调 `parseTex(raw)`，`loadTexImage` 内部再调一次，
`decodeTex` 内部 `parseTexInternal` 第三次。压缩容器的解压是**顺序**的且很贵
（60.8Mpx 约 250ms）。修法：把已解析的 `info` 传下去复用
（`loadTexImage(raw, opts, infoPre)`），省掉一次解压。

### ④ 实测收益（三臂交替，各 3 次，全部像素一致）

| 臂 | 渲染耗时（3 次） | 中位 | 相对基线 |
|---|---|---|---|
| **A** 基线（复用关 + 预解码关） | 4135, 4250, 4031 | **4135ms** | — |
| **B** 仅复用 `parseTex` | 4300, 3909, 3924 | **3924ms** | **−211ms** |
| **C** 复用 + metaOnly 预解码 | 3943, 3611, 3608 | **3611ms** | **−524ms（−12.7%）** |

**三臂的 `canvasSum` 全部 = 51060945（逐位一致）。**

- 复用 `parseTex`：**−135ms**（比预解码本身还大）
- 块行并行预解码：**−47ms**（远低于解码侧的 −517ms）

### ② 第三个 bug：候选扫描把每个 mip0 都解压了一遍（−47ms 的真相）

预解码**第一版**只值 **−47ms**（C−B，上一轮实测），远低于解码侧的 −517ms。
开销账很清楚：pass 自身 390ms，其中 worker 只干 171ms，**~220ms 耗在候选扫描**
—— `collectPredecodeCandidates` 要把 65 个 .tex 全 `parseTex` 一遍，而
`parseTexInternal` 在 mipmap 循环里**内联解压**（`lib/pkg-extract.js:350`），
**早于** GIF 标志的读取（`:353`）。于是 `鸟_00020` 的 60.8MB 被白白解压，
而它随后就被"动画图集"这一条排除。

**修法（`metaOnly`）**：

1. `parseTexInternal(data, { metaOnly })` 只读 mipmap 元数据、**不解压**
   —— `Reader.bytes` 本身只返回视图（`subarray`，不复制），所以只需跳过
   `lz4DecompressBlock`；顺带暴露 `storedLength` / `payloadLength` 供体积校验。
2. 主线程筛选改用 `metaOnly`；候选改为携带**整个容器** `raw` 而不是 mip0 像素。
3. **整容器解析 + 解压搬进 worker**（`predecode-worker.mjs`），解压因此也并行；
   同一纹理的多个带在 worker 内共享一次解析。

修好后 `warmMs` **390 → 219–237ms**，预解码净收益 **−47ms → −313ms**。

**顺带修掉第四个 bug**：`parseTexInternal:404` 在 metaOnly 下会读
`mip0.bytes.length`（`bytes` 为 null）→ **每张纹理都抛 `null.length`**，
候选静默变成 **0 个**（`textures:0`）。加 `!mip0.bytes` 保护后恢复正常。
守卫里补了对应的结构性检查。

**一个额外收获**：metaOnly 探针直接暴露了存储尺寸的真实形态 —— 它们被**补齐到
64 的倍数**：

| 纹理 | 逻辑尺寸 | 存储尺寸 | 块列数（逻辑/存储） |
|---|---|---|---|
| `栏杆` | 3281×2160 | **3328×2176** | 821 / **832** |
| `背景` | 3840×2160 | 3840×**2176** | 960 / 960 |
| `左大衣` | 1872×1760 | **1920×1792** | 468 / **480** |

`栏杆` 差 **11 个块**、`左大衣` 差 **12 个块** —— 这正是 bug 1
"第 0 块行看着正常、其后逐行漂移"的量化解释：用逻辑尺寸算块列，每往下一行
源偏移就偏一个块。

## 三十、效果链的前提实测：一次被交替测量推翻的结论

本轮**没有改动任何运行时代码**，只做测量与定位。结论有一条是**撤回**。

### ① 前提：效果到底挂在哪些对象上（场景数据，不是推断）

剖析表只给"效果 × 名称"的耗时，**不给效果→对象的归属**。上一轮我曾据此把
`opacity` 388ms / `color_grading` 267ms 归给 `鸟_00020`，并当场标注"归属未取证"
—— 本轮用场景数据查实，**归属是 `栏杆`，不是 `鸟_00020`**：

```
栏杆  image=models/栏杆.json  size="3281.00000 2160.00000"
      effects=[effects/opacity/effect.json,
               effects/workshop/2795521260/color_grading/effect.json]
```

`3281×2160 = 7.09 Mpx` 与剖析表的"效果输入纹理尺寸 opacity 均值 7.09 Mpx n=1"
完全吻合。于是 `栏杆` 的 957ms 拆得开了：

| 组成 | GPU 实测 |
|---|---|
| 纹理解码（已由 §二十九 并行化） | ~205ms |
| **`opacity`** | **388ms** |
| **`color_grading`** | **267ms** |
| 光栅化等 | ~97ms |

**两个全表面效果占了 `栏杆` 的 655/957 = 68%**，而它们作用在**同一个 7.09Mpx
缓冲**上。

### ② 一个被推翻的结论（重要）

单次运行 `--cpu` 给出的数字是：效果链 **688ms**（GPU 路径 1131ms）——
看起来"GPU 在效果链上是净损失，CPU 快 443ms"。我差点据此动手。

改用**交替重复**（各 3 次，同进程条件）后，结论**完全相反**：

| | GPU 路径（3 次 / 中位） | CPU 路径（3 次 / 中位） |
|---|---|---|
| 效果链 | 1071, 1192, 1147 → **1147ms** | 3677, 3867, 3427 → **3677ms** |
| 渲染合计 | 3922, 4079, 4121 → **4079ms** | 6701, 6895, 6347 → **6701ms** |

**GPU 在效果链上是 3.2× 的收益，整体 1.64×。** 与 §二十八 同一条教训：
**跨进程单次测量在这个场景上完全不可信**（同一配置先后跑出 688ms 与 3677ms，
差 5.3×，远超任何效应量）。**"GPU 是净损失"这一结论已撤回**，不要据此改默认值。

### ③ 发现：`runEffectChainOnGL` 已实现但**从未被调用**

`lib/we-renderer/gpu-gl/gl-effect.js:495` 有一个链式执行器，注释自称：

> 连续效果链在 GPU 内执行 (FBO 乒乓, 中间结果不读回 CPU)。
> 4 次独立调用 ~400ms → 单会话 ~35ms, 91% 节省。

全库搜索只有它自己的定义，**没有任何调用方**（与 §二十九 ⑤ 里
`parallel.js`/`decode-worker.mjs` 是同一类问题）。

它正好对上本轮定位到的成本：`栏杆` 的 `opacity` → `color_grading` 是两个连续
的全表面效果，各自单独走 GPU 时每趟都要
**上传 28MB + readPixels 读回 28MB**，链式执行只需首尾各一次。

### ④ 为什么本轮没有接线（诚实说明）

接线点是 `effects.js::_applyEffectsImpl` 的效果循环 —— 这是整个渲染器**最热且
最敏感**的路径，scratch 缓冲池借还、显存泄漏修复、退化保护、逐效果计时全在里面。
正确接线还需要：

1. 把 `_tryEffectGpu` 拆成"只准备 program/uniform"（`_prepareEffectGpu`）与
   "执行"两半，链路径复用前半；
2. 在效果循环里做**前视**，收集连续可链的效果（跳过判定必须与主循环同源，
   不能复制一套 —— 本会话已多次吃过"两套公式漂移"的亏）；
3. 确认 `runEffectChainOnGL` 对 i>0 的效果确实用**中间结果 FBO** 覆盖
   `g_Texture0`（而不是仍绑原图）；
4. 断言链式结果与"逐效果单独走 GPU"**逐位一致**（两者中间态都是 RGBA8，
   应当恒等）。

本轮剩余预算不足以把 1–4 做完并验证，而"像素逐位一致"是本会话贯穿始终的硬
不变量。**在证据不足时改最热路径，是比"暂不接线"更差的结果**，故停在测量层，
把它列为下一步。

### 作用域提醒

以上都是**场景特定**：`栏杆` 这个对象恰好挂了两个全表面效果。
`鸟_00020` 在 effects 探针的 39 个对象里**根本不出现 —— 它没挂任何效果**，
所以链式执行对它的收益是 0，它的 1417ms 全在光栅化上。

## 三十一、链式执行的尝试：机制正确，但拆分会改变"谁走 GPU"，已回退

本轮按 §三十 的计划接线了 `runEffectChainOnGL`，**跑通并取得一条正面结果，但
最后整段回退**。两边都记下来。

### 做出来的东西

| 部分 | 内容 |
|---|---|
| `gpu-gl/chain-allowlist.js`（新） | 白名单 `{opacity, color_grading}` + 上限 4。进白名单必须带实测数字 |
| `adapter.js` | `_tryEffectGpu` 拆成 `_prepareEffectGpu`（只编译 + 组装 uniform）+ 执行；新增 `_tryEffectChainGpu` |
| `effects.js` | 索引循环 + 前视收集连续白名单效果 + `chainSkip` 跳过已消费项；可选自检 `DSH_WE_CHAIN_VERIFY=1` / A/B 开关 `DSH_WE_NO_FX_CHAIN=1` |

### 正面结果：链式与逐效果**逐位一致**（这条断言成立）

开启自检后，在真实场景上对 `栏杆` 的 `opacity+color_grading` 链实测：

```
链式自检 opacity+color_grading: 差异字节 0/28347840 (0.0000%) 最大通道差 0
```

链与逐效果的中间态都是 RGBA8，**确实恒等** —— §三十 里"应当逐位一致"的推断
得到实测确认。这条本身是有价值的：机制没有引入额外量化误差。

### 负面结果：为了复用 program/uniform 而拆分 `_tryEffectGpu`，改变了谁走 GPU

拆分之后，`走GPU效果数` 从 **25 掉到 21**，画布 `canvasSum` 由
`51060945` 变为 `131317897`。注意 `nonzeroBytes` 只差 **68 字节**
（33177062 → 33177130）—— 是很细微的差异，不是整层错乱，**目视基本不可能发现**。

**我的第一个假设被实测否证**：我以为原因是把函数体移出了 `try`
（`buildUniforms`/`loadTexture` 抛错时不再走 `_noteGpuFailure` + 回退 CPU，
而是冒泡上去让整个效果被跳过）。把函数体重新包回 `try` 之后，**仍然是 21**。

随后确认这不是链式造成的：**关掉链式（`DSH_WE_NO_FX_CHAIN=1`）同样是 21**，
说明问题出在 `_tryEffectGpu` 的拆分本身，与链式逻辑无关。

（顺带：在出问题的状态下链式也没有更快 —— 效果链 784ms（关）vs 1015ms（开）。
但这个对比被"谁走 GPU 变了"污染了，**不作为链式性能的结论**。）

### 处置：整段回退

回退后**精确复现**已知良好状态：

| | 回退后 | 出问题时 |
|---|---|---|
| `走GPU效果数` | **25** | 21 |
| `canvasSum` | **51060945** | 131317897 |
| 效果链 | 1024ms | 784 / 1015ms |

`npm run verify` 全绿，打包白名单 `missing=[]`，临时文件 `chain-allowlist.js`
已删除（不留未接线模块）。

### 为什么回退而不是继续调

**在一个"4 个效果悄悄从 GPU 回落到 CPU"的机制没查明之前，改渲染器最热路径
是不可接受的** —— 而它能被发现的唯一原因是画布校验和（`nonzeroBytes` 只差
68 字节）。本会话从头到尾守的硬不变量是"像素可复现"，这条被破坏时就必须退。

### 下一步（已把范围缩到最小）

问题已经收敛成一个很窄的可判定问题：**拆分 `_tryEffectGpu` 前后，是哪 4 个
效果从 GPU 回落到了 CPU？** 建议做法：在 `_tryEffectGpu` 里对每个
`(对象, 效果名)` 记录**走出原因**（prepare 失败 / 尺寸不符 / 执行抛错 / 成功），
重构前后各跑一次取差集 —— 这是纯取证，不需要再猜。

`runEffectChainOnGL` 保持**预先存在的未接线状态**；本轮不为它留下任何新模块。

## 三十二、分辨率扫描：推翻"填充率"假设，并修正一处地板估计

### 测量：同一场景、同一 t，只改画布尺寸

| | 4K (3840×2160) | 1080p (1920×1080) | 面积 = ¼ |
|---|---|---|---|

| 纹理解码 | 1702ms | 1632ms | ~持平（与画布无关，符合预期） |
| 效果链 | 1086ms | 1002ms | ~持平 |
| **`鸟_00020`** | **1261ms** | **980ms** | **−281ms（仅 −22%）** |

`鸟_00020` 的 6 个实例共享同一张 5.5MB 帧纹理（`_atlasFrameReqs=1` 证明后续实例
在缓存键上早退，没有重复解码），所以也不是重复解码。

### 修正：我此前的地板划分是错的

§二十九 / §三十 里我把可达下界写成

> 解码 ~620ms + 效果链 ~1130ms + **光栅化 ~913ms** ≈ 2828ms

其中"光栅化 ~913ms"是用 `渲染合计 − 解码 − 效果链` 倒推出来的**残差**，
我把它当成了"绘制像素的不可压缩成本"。本轮测量表明这个假设站不住：
**那 ~900ms 里绝大部分与画布面积无关**，因此它不是"填充率成本"，
更像是某种**每对象固定开销**（尚未定位）。

**后果**：不能再引用"效果链 1130 + 光栅 913"这个划分去论证下界。<2500ms
是否可达**目前是未定的** —— 既不能断言可达，也不能再按旧划分断言不可达。
这一点必须如实改成"未定"，而不是继续沿用旧的 2828ms。

## 三十三、插桩取证：找到那笔与画布无关的开销（−756ms，逐位一致）

§三十二 的插桩建议直接执行了，**一次就定位到根因**。

### 插桩

| 位置 | 内容 |
|---|---|
| `canvas.js` | 用包装（不改函数体）给 `blit` / `blitScaled` / `blitRotated` 计时，键 `绘制:*`；关闭剖析时完全不安装 |
| `image.js` | 给 `loadModelTexture` 计时，键 `对象内部:取纹理` |

### 取证结果（4K / 3486806915 / GPU）

| 项 | 耗时 | n |
|---|---|---|
| **`对象内部:取纹理`** | **1515ms** | 35 |
| `绘制:blitRotated` | 465ms | 10 |
| `绘制:blitScaled` | 316ms | 36 |
| `鸟_00020 [image]` | 1250ms | 6 |

**立刻排除两条**：全部绘制内核加起来只有 **781ms**，而 `鸟_00020` 一个对象就 1250ms
且几乎没有绘制成本；`鸟_00020` 的 6 个实例又共享同一张帧纹理。所以钱花在
**取纹理**上。

### 根因：`parseTex` 在**帧缓存命中之前**执行

`core.js::_loadTextureImpl` 原先的顺序是：

```js
let raw = this.pkg.read(texPath);
if (raw && opts && opts.time != null) {
  texInfo = parseTex(raw);              // ← 解压整个容器 (鸟_00020 = 60.8Mpx ≈ 250ms)
  const rect = atlasFrameRect(texInfo, opts.time);
  if (rect) {
    cacheKey = texPath + '#' + rect.index;
    if (this.textureCache.has(cacheKey)) return ...;   // ← 缓存命中在这里才发生
```

**同一张纹理的 6 个实例，各自把 60.8MB 容器完整解压一遍**，
最后只有第一个真正解码，其余 5 个解压完就命中缓存返回。约 **1500ms 纯浪费**。

**这也解释了 §三十二 的谜题**：为什么分辨率降到 1/4、`鸟_00020` 只降 22% ——
因为那笔钱根本是**解压**，解压与画布尺寸无关。上一轮我测出了现象
（"不是填充率受限"）但没能定位原因，这一轮用插桩定位了。

### 修法（无损）

按 `texPath` 记忆**帧表元数据**（尺寸 + 帧数组，很小），
`parseTex` 只在第一次做：

```js
let meta = noMemo ? null : this._atlasMeta.get(texPath);
if (!meta) { const info = parseTex(raw); meta = { width, height, frames }; ... }
const rect = atlasFrameRect(meta, opts.time);
```

刻意**不**留存整容器解析结果（它带 60.8MB 解压缓冲，常驻内存不可接受）；
`atlasFrameRect` 只需要 `{width, height, frames}` 三个字段，而守卫脚本早就用

## 三十四、效果链内部：一条被否定的假设（没有重复编译）

沿用 §三十三 的方法，但这次**零产品代码改动**：在诊断 harness 里包装原型方法计时
（`DSH_WE_TPROF=1`）。上一轮的教训是"改热路径会扰动 GPU 效果数"，包装法完全避开
这个风险。

### 读数（4K / 3486806915 / GPU / 含预解码，渲染 2910ms）

| 包装项 | 总耗时 |
|---|---|
| `applyEffects` | 1046ms |
| `_tryEffectGpu` | 1043ms |
| **`_compileWorkshopEffect`** | **478ms** |
| `_readGlslShader` | **0ms** |
| `loadTexture` | 559ms |
| `loadModelTexture` | 514ms |

`applyEffects ≈ _tryEffectGpu` ⇒ 效果链的时间**几乎全在 GPU 路径里**（符合预期，
25/26 个效果走 GPU）。而其中 **478ms（45%）在 `_compileWorkshopEffect`** ——
一个自称"编译并缓存"的函数，35 次调用共 478ms，**看起来很可疑**。

### 假设：缓存没生效，每次都在重编译

**被实测否定。** 逐次耗时：

```
27.0, 211.4, 80.5, 0.0, 0.0, 14.8, 0.2, 10.0, 0.1, 0.0, 0.0, 0.0, ... ,
113.5, 0.0, 0.0, 0.0, 11.5, 0.1, 0.0
```

**绝大多数调用是 0.0ms（缓存命中）**。478ms 集中在 **7 次首次编译**
（211.4 + 113.5 + 80.5 + 27.0 + 14.8 + 11.5 + 10.0 ≈ 469ms），
即每个不同效果名在本进程里首次编译一次。`GLSL_CACHE_MAX = 24`、
本场景只有 8 个不同效果名 ⇒ **不存在淘汰抖动**。

**结论：这不是 bug，是真实的一次性编译成本 —— 此处没有收益。**

### 这条否定结果的推论

效果链 ≈1040ms 的构成大致是：

| 部分 | 量级 | 能否优化 |
|---|---|---|
| 首次 GLSL 编译 | ~470ms | **不能**：编译产物含闭包（`integration.js:13` 注释），无法跨 worker 传递，也无法跨进程缓存；冷渲染必须付 |
| GPU 执行 + uniform 组装 + 上传/读回 | ~570ms | 只有链式执行能压（省掉中间 readPixels），即 §三十一 那条被卡住的路 |

所以**效果链上唯一还剩的无损杠杆，仍然是链式执行**；而它的前置条件未变：
先查明"拆分 `_tryEffectGpu` 为什么会让 4 个效果从 GPU 回落"（§三十一）。
本轮没有推进那件事，因为上一轮已经用一次失败证明了在机制不明时动那条路径的代价。

### 方法沉淀

`DSH_WE_TPROF=1` + 原型包装 = **在诊断层观测产品内部，产品代码零改动**。
比 §三十三 往 `canvas.js`/`image.js` 里插计时更安全，后续取证优先用这个。

## 三十五、链式执行：改用"严格加法"重做成功，但收益远小于注释自称

§三十一 的链式执行**已接线并保留**。这次换了做法，先过验收，再看收益 ——
收益比预期小得多，一并如实记录。

### 做法：不改 `_tryEffectGpu`，宁可重复

§三十一 失败的原因是"为了复用 program/uniform 而拆分 `_tryEffectGpu`"。
这次**一行都不改它**，`_tryEffectChainGpu` 自包含地重复约 20 行 uniform 组装。

为什么重复是可接受的：重复只可能造成**少串一条链**（错过优化），
不可能改变单效果路径的行为。反过来拆分则会改变行为，且已经发生过一次。

### 验收：两条硬指标都回到已知良好值

| 指标 | §三十一（拆分） | **本轮（严格加法）** | 已知良好 |
|---|---|---|---|
| `走GPU效果数` | 21 | **25** | 25 |
| `canvasSum` | 131317897 | **51060945** | 51060945 |

**这同时反证了 §三十一 的判断**：那次回归确实由拆分 `_tryEffectGpu` 引起，
而不是链式逻辑本身 —— 同一套链式逻辑在不拆分时，两条指标都完好。

### 逐位一致性（运行期自检，DSH_WE_CHAIN_VERIFY=1）

```
链式自检 opacity+color_grading: 差异字节 0/28347840 (0.0000%) 最大通道差 0
```

链式与"逐效果单独走 GPU"**逐位一致**（两者中间态都是 RGBA8）。

### 实测收益：−36ms（−1.3%），比预期小一个数量级

交替重复各 4 次（`DSH_WE_NO_FX_CHAIN=1` 做对照），**8 次 `canvasSum` 全部 = 51060945**：

| 臂 | 4 次读数 | 中位 |
|---|---|---|
| 链式 ON | 2794, 2851, 2870, 2862 | **2856ms** |
| 链式 OFF | 2909, 2899, 2863, 2885 | **2892ms** |

**Δ ≈ −36ms（−1.3%）。**

### 为什么只有 36ms：执行器注释里的"91% 节省"不可外推

`runEffectChainOnGL` 的注释写着"4 次独立调用 ~400ms → 单会话 ~35ms, 91% 节省"。
本场景实测只省 ~36ms。原因：**单效果的成本由着色器数学主导，不是上传/读回往返**。
`color_grading` 单独走 GPU 是 267ms，链式把两次往返压成一次，
省下的那一趟（约 30ms 量级）就是全部收益 —— 数学本身仍要算两遍，一遍也少不了。

注释里那个 91% 是在 4096×4096 上跑**极廉价**着色器（identity 类）测出来的，
**不可外推到真实效果**。这条已在此更正。

### 为什么仍然保留

1. 无损：逐位一致，且 `走GPU效果数` 不变；
2. 净为正：−36ms 虽小，方向稳定（4 对里 3 对更快）；
3. 它把 `runEffectChainOnGL` 从"**已实现但从未被调用**"变成真正接线 ——
   这是 §三十 起就挂着的遗留项。

### 护栏：`scripts/verify-fx-chain.mjs`（12 项，已接入 `npm run verify`）

最关键的一条是 **`_tryEffectGpu` 未被拆分**（体内不得出现 `_prepareEffectGpu`）——

单会话上限、A/B 开关、前视判据的**保守方向**（判据不同步只会少串、不会串错）、
主循环行为不变、以及"运行期逐位自检机制存在"（需要 GPU，故只能离线断言机制本身）。

三条自建守卫合计 **115 项全绿**（图集 53 + 块行 50 + 链式 12），

## 三十六、最后一个未分解的大项：旋转绘制（实测"不做"）

§三十五 结尾我说"可预见的无损手段已全部用尽"。**那也是断言，不是测量。**
本轮把剩下最大且未分解的一项 —— `绘制:blitRotated` **435ms / 10 次**（43.5ms/次，
是 `blitScaled` 的 12 倍）—— 拿去实测。

### 假设与实测

`blitRotated` 按**旋转后的包围盒**逐像素扫描，再逐点做逆旋转 + 判是否落在四边形内。
包围盒面积是四边形的 `(|cos|+|sin|)²` 倍 ⇒ **我假设 45° 时会白扫一半**。

实测（复算 bbox 迭代数 vs 真正命中的像素数）：

```
blitRotated 10 次: bbox 迭代 36140678  四边形内 30003289  白扫 17.0%
```

| 角度 | 尺寸 | bbox | 命中 | 白扫 | 耗时 |
|---|---|---|---|---|---|
| **7.1°** | 1920×720 | 1.30M | 1.05M | 19.3% | 19.1ms |
| **7.1°** | 2688×1008 | 2.27M | 1.82M | 19.6% | 33.1ms |
| **7.1°** | 3840×1440 | 4.92M | 3.96M | 19.4% | 56.9ms |
| **7.1°** | 4416×1656 | 8.29M | 6.26M | 24.6% | 126.7ms |
| **7.1°** | 4992×1872 | 7.33M | 6.35M | 13.4% | 112.4ms |
| **7.1°** | 5760×2160 | 8.29M | 7.26M | 12.5% | 127.7ms |
| 0.7° | −2443×1201 | 1.93M | 1.89M | 2.1% | 42.6ms |
| 8.8° | −340×453 | 0.20M | 0.15M | 24.2% | 4.1ms |
| −6.9° | 699×642 | 0.56M | 0.45M | 19.7% | 7.9ms |
| 11.0° | 1243×812 | 1.05M | 0.81M | 22.4% | 13.5ms |

**假设被推翻**：白扫只有 **17.0%**，不是 50% —— 因为本场景的旋转角只有 **7.1°**
（`(|cos|+|sin|)²` 在 7.1° 时约 1.15，不是 45° 的 2.0）。

### 判定：不做（有数字依据）

精确逐行求 x 跨度的收益上界 = `435ms × 17.0% ≈ 74ms`。而它要改的是**旋转 +
双线性采样**这段像素最敏感的代码 —— 本会话的硬不变量是逐位一致，
**74ms 换这条路径的风险不划算**。这是一次**有测量依据的"不做"**，不是遗漏。

### 顺带确认：`鸟_00020` 的 476ms 是真实工作量

6 个 `鸟_00020` 实例（全部 7.1°）合计 **475.9ms**，且每次的包围盒都≈**整张画布**
（3840×2160 = 8.29M 迭代）—— 也就是说它有 6 次**近乎全画布的双线性采样**
（约 30M 目标像素，≈105 Mpx/s）。四边形比画布还大（最宽 5760 > 3840），
**没有可裁掉的边**。这是真实工作量，无损手段削不动。

### 结论

"无损手段已用尽"现在**有测量支撑**，不再只是断言：最后一个未分解的大项
（旋转绘制 435ms）经实测只有 74ms 的理论余量且风险过高。

要突破 `<2500ms`，只剩**需要用户明确同意**的有损路线（超大纹理按绘制尺寸解码，
§二十七/§二十八 记录在案），或转向 PNG 编码（~205ms）这类更小的项。

## 三十七、按效果对照 GPU / CPU：最后一条路由想法被否证

### 假设

`栏杆` 的两个全表面效果合计 655ms（7.09Mpx）。我推断瓶颈是 **readPixels 回读**
（每次 28MB，~90MB/s ⇒ ~300ms/次），并由此推断：对**数学极简**的效果
（`opacity` 就是一次乘法），GPU 的上传+回读往返可能比 CPU 逐像素**更贵**。
若成立，则可按效果名做一张"实测路由表"（简单效果走 CPU），是无损收益。

### 实测：把效果全部赶到 CPU 做对照

在诊断脚本里包装原型方法（`DSH_WE_NO_FX_GPU=1`，**产品代码零改动**），
交替各 2 次：

| 效果 | GPU | CPU | 结论 |
|---|---|---|---|
| `opacity` (n=1, 7.09Mpx) | 661, 665ms | 678, 706ms | GPU 略快（~3%） |
| `foliagesway` (n=3) | 146, 147ms | 449, 455ms | **GPU 快 3.1×** |
| `waterwaves` (n=20) | 176, 180ms | 214, 217ms | GPU 快 ~1.2× |
| `auto_sway` (n=5) | 35, 35ms | 39, 39ms | GPU 略快 |
| **效果链小计** | **1019, 1028ms** | **1381, 1419ms** | **GPU 快 1.36×** |
| 渲染合计 | 3124, 3126ms | 3505, 3518ms | GPU 快 ~12% |

**假设被推翻**：`opacity` 在 CPU 上并不更快（678 vs 661）。也就是说
**GPU 往返并没有比 CPU 逐像素更贵**，本场景**每一个**效果都是 GPU 更快。

**结论：按效果做 CPU/GPU 路由表无收益，不做。** 这是最后一条"换个执行器"
的想法，现已被实测排除。

（附带确认：`opacity` 那 661ms 是**链式** opacity+color_grading 的合计 ——
链式把 color_grading 并进同一次会话后，计时归在链的首个效果名下，
与未链式时的 388+267=655ms 基本持平，再次印证 §三十五 的 −36ms 量级。）

### 至此：无损手段的证据链已闭合

| 大项 | 量级 | 实测结论 |
|---|---|---|
| 纹理解码 | ~430ms | 已从 2259ms 压下来（按帧解码 / 复用 parse / 块行并行 / 帧表记忆），不能再压 |
| 首次 GLSL 编译 | ~470ms | 不可压：产物含闭包，无法跨 worker 或跨进程复用 |
| GPU 效果执行 | ~530ms | GPU 已是最快执行器（本 §），链式余量仅 −36ms |
| 旋转双线性绘制 | ~476ms | 真实工作量，白扫仅 17%，改动风险高于收益 |
| PNG 编码 | ~205ms | 无损的只有压缩级别（改文件大小，不属本轮目标） |

**渲染 ≈2856ms、用户可见 ≈3060ms**（起点 4529ms，−32%）。
`<2500ms` 在**只用无损手段**的前提下不可达 —— 这条现在有逐项实测支撑，
不再是估算或断言。要突破必须由用户在有损路线上做出选择
（超大纹理按绘制尺寸解码：`鸟_00020` 绘制面积仅为图集的 2.3%–20.5%，
收益上界很大，但会产生观感取舍）。
