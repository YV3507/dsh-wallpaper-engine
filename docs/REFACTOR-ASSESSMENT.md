## 1. 决策（先结论）

**不做立刻的结构性大重构**：先做一轮「减重 + 加固」，再按已验证的接缝分批抽取。

三条依据：① 病灶是**体量集中 + 边界缺失**（两个门面文件仍占手写代码约 27%），不是逻辑纠缠；② 守卫是唯一的安全网，
大重写会先拆掉它，而缺陷率与回滚史说明"一次改对"不成立；③ 当前最高风险曾是**零 CI**，已先补掉。

**顺序**：`P0 加固 ✅` → `P1 单一真源 + 零耦合抽取 ✅` → `P2 按接缝分批`（P2-9/P2-10 ✅，P2-11 🟡）→ `P2-12 静态帧线整体移除 ⬜`。
**并行功能轨道**：`F 字体系统大改`（F0/F1/F2 ✅，F3 ⬜）—— 它的数据模型建立在 P1-5 之上，故排在其后。

### 3.5 E：`apply(ctx)` 拆分的必要性评估

> 复算：`node test/tools/analyze-host-apply.mjs`。
> **结论：不整体重写** —— 先做三条前置，之后**按路由族拆、一次一族**。触发条件见 §7 第 6、7 条。

**为什么不现在拆**：① 没有具体病痛指向它（对比 P2-9：那时有 26 处裸 `fetch` 的具体隐患）；② 代价是 **24 个共享可变闭包状态**
—— 某个 `register*` 拿到**拷贝**而不是引用会**静默**出错（路由偶发 404 / 统计错乱，最难定位）；③ 宿主侧安全网比客户端薄；
④ 没有"必须现在做"的外部压力。

**三条前置**（已全部就绪）：① 路由索引 `docs/ROUTE-INDEX.md` + `verify-route-index.mjs`；② 三条零覆盖路由补真实行为断言；
③ 巨石闭包状态清单（`host-route-index.mjs --deps`）。
⚠️ 第 ③ 步顺带更正一个**误测**：早期把"到下一个同级声明的距离"当体量，量成 1,795 行；真值 **293 行 ≈ `apply` 的 15%** ⇒
`apply` 不是"几块大肉"，而是 **~30 个中等处理器 + 助手共享 24 个闭包状态** ⇒ **更支持按族拆**。

**每族的固定动作**：① 新建 `lib/routes/<族>.js`，导出 `register<族>Routes(webServer, c)`，族内共享的随族搬走；
② `apply` 里改成一次调用，**共享可变状态只以引用进 `c`，不做拷贝**；③ 重新生成 `docs/ROUTE-INDEX.md`；④ 该族的守卫必须先存在。
后续族：`inventory` → `upload` → `scene` → `media`；被多族复用的助手（`serveFile` / `handleSceneFiles`）留在 `apply` 里、以引用进各族 context。

### 3.6 P3 的来源：**未归口 / 未声明需求**的判定依据

**方法**：四路并行**只读**审计（守卫是否"无牙" / 类型与打包面 / 结构重复 / 活文件内的零调用点代码）＋ 客户端与文档侧自查。
每条结论都要求 `file:line` 与可复算命令；可达性测量已提升为入库工具 `test/verify-reachability.mjs`。

**关键实测**（都能由 §8 命令复算）：路由索引 vs 运行时注册 **31 == 31**（已成守卫）· 剪掉两条**假活锚点**后
`lib/` 曾 **48 文件 / 9,618 行不可达**（P2-12 第一半已删净 ⇒ 现为 **0 / 0**）· `lib/types/*.d.ts` 字段差（`WallpaperDescriptor` 缺 10、`Inventory` 缺 3、`client.d.ts` 零值导出）·
`WallpaperPicker` 体量 · `TODO.md` 是否入库（**否**，却被 17 处引用）。
**结论**：存在未声明 / 未归口的需求共 **22** 条 → 归口为 §5 的 **P3-1 … P3-22**。

## 6. 设计基线：静态帧线移除后的回退形态

> 适用范围：**场景类壁纸**（网页壁纸的形态与垫底不在本节）。原则：**零迁移优先** / 不新增用户可见开关 / 不留死代码。
>
> ⚠️ **不要把 `fork/legacy/static-frame-render` 合进本线**：它是"完善静态帧渲染"的另一条路线，与本节目标（**整体移除**，= §5 P2-12）**方向相反**，已搁置。两条线在 `edd2d59` 处分叉，各自独有 83 / 33 个补丁（等价补丁仅 2 个）⇒ 合并且是语义冲突。

### 6.1 现状：有**两层**，别把两层混成一层

| 层 | 是什么 | 落点 |
|---|---|---|
| **显示链** | 屏上"动态还是静态" | `src/client.js` `buildMedia` |
| **静帧来源枚举** | 静态时那张图由哪个来源产出 | `FRAME_VARIANTS` |

显示链（源码注释称"优先级不变量"）：`① live（WebWallGL） → ② sceneVideo（作者内嵌 MP4，poster = 静帧） → ③ 静帧图（/scene-frame?v=N）`。

### 6.2 现状：静帧来源档位（本仓库的真实档位）

| 档 | 标签 | 宿主的真实来源 |
|---|---|---|
| **0** | 合成（分层） | `tryCompositeSceneLayers()` 多层合成；**失败则静默回落到单图排序** |
| **1** | 主纹理 | **找最大图片**：遍历包内 `.tex`，按 `面积 × 嵌入格式权重 × 路径惩罚` 打分 |
| **2** | 作者原画 | 包内嵌入 JPEG/PNG 整图按面积置顶 |
| **3** | 预览图 | 直接读工坊目录 `preview.jpg\|png\|gif`（**不经** `pkg-extract`） |
| **4** | 自定义画面 | 用户导入的 `overrides/<id>.*`，缺失 → 422 |

**GPU 实时帧（`<key>_gpu.png`）优先于 v=0–3 的全部档位；v=4 豁免**。它由 live 渲染页经 `PUT /scene-frame-cache/<token>` 回填
—— **它是"实时帧缓存"，不是静态帧产物**（此区分决定了它的去留）。

### 6.3 「静态帧渲染」的完整血统 —— 它**不只是**那个离线渲染器

**找最大图片**（`3666a66`，这条线的开山提交）· **作者 PNG**（同批）· **合成（分层）** · **离线渲染器**（更早）**同属一条线，应当一起走**。
⇒ 整条线一起移除：`extractSceneMainImage*`（**含合成**）、渲染器，以及档位 `1/2/3`。

### 6.4 ⚠️ 一个会从后门活下来的陷阱：`v=0` 的静默回落

```js
if (!variant) {
  try { const composite = tryCompositeSceneLayers(scene, access, label); if (composite) return composite; }
  catch { /* fall through to the single-texture path */ }
}
let candidates = [];        // ← 「找最大图片」就从这里继续活着
```

**只要合成路径还在，删掉 `v=1/v=2` 这两个"档"并不能把「找最大图片」移出自动链。** 本设计因此**连合成一起移除**，
从根上断掉这条回落 —— 这也是 §6.12 要求探针覆盖到 `collectImageObjectTextures` / `FORMAT_PENALTY` 等**实现标识**的原因：**防它换条路径回来**。

### 6.5 现状取证：离线渲染器**已经是死代码**

入口 `lib/index.js` `renderSceneFrameInWorker` **只有定义、无调用点，且未导出**（该文件只导出 `inject` / `apply` / `default`）。
`/scene-frame` 注释写明"不再先试 `SceneRenderer` worker"。beta 场景动画（多帧/APNG）已移除，`verify-client.mjs` 有**反向探针**断言其永不复活 —— P2-12 沿用同一手法。

### 6.6 目标显示链（唯一权威顺序，5 级）

```
① live（WebWallGL 实时渲染）
② sceneVideo（作者内嵌 MP4，/scene-video）        ← 与 ① 同属「动」；作者本意
③ 实时抓帧缓存（场景 _gpu.png / 网页 liveFrame）  ← 「静」的链头；真实画面，不是猜图
④ 自定义画面（用户导入 overrides/）               ← 用户显式资产
⑤ 空（不渲染）                                   ← 全链不可用时的诚实终端
```

**①→② 顺序不变**（本次只移除静态帧线，不借机改这条已验证的顺序）· **③ 优先于 ④**（与宿主 `gpuFrameFileFor()` 的既有语义一致）·
**没有 ⑥，明确不做**：不再有任何"替作者猜一张图"的来源 —— 找最大图片 / 作者 PNG / 合成**正是**在干这件事。

### 6.7 目标档位与默认

| id | 名称 | 说明 |
|---|---|---|
| **0** | **自动** | **取链头**（③→④ 中第一个可用者） |
| **4** | 自定义画面 | 沿用既有 id |

**移除 id `1/2/3`**：宿主侧对 `1/2/3` 及越界值一律 **clamp 到 0**。值域里的洞（缺 1/2/3）**有意保留**（让"哪些档已退役"在数据里可读，且避免值域迁移）。
**默认 = 链头**：`GET /scene-frame/<token>`（无 `?v=`）不再隐含"档 0 = 合成"；`?v=4` 仍是"强制自定义画面"（缺失 → 422）。

### 6.8 失败语义与终端

| 环节 | 目标行为 |
|---|---|
| live 首帧逾时 / 运行期失联 | 记 `sceneLiveFailures[id]` → 前进到 ②；**同会话对该壁纸不再重试 live**（现状即此，保留） |
| ② 内嵌 MP4 | 取不到 → 静默前进；**不记失败记忆**（作者没给视频是常态，不是故障） |
| ③ 实时抓帧 / ④ 自定义画面 | 缺失 → 逐级前进 |
| ⑤ 空 | **留空** + 状态行给出可判定原因；**不回落任何"猜图"来源**，也不回落预览图 |

### 6.9 零迁移论证（含一处**与现状冲突**的点，需拍板）

用户可感知的语义不变：**"我为这张壁纸 pin 过一个来源"这个事实仍被记住**。被移除的 pin 值（`1/2/3`）**clamp 到 0（自动）** ⇒ 旧配置**原样可用**，
只是那条 pin 变成"自动"（这是唯一可接受的降级方向）。`customFrames` 形状与 `sceneLiveFailures` 值域不变。

⚠️ **冲突点**：原稿要求三个键同时存在于"客户端发送 / 宿主白名单 / 客户端读回"三份清单，而现状 `frameVariants` 与 `customFrames`
被显式钉为**客户端独占**（`verify-client.mjs` 的 `CLIENT_ONLY`），宿主白名单里没有它们。二者必须二选一，并在**同一提交**里把注释、守卫、文档一起改：
**方案 A（推荐）**：承认"客户端独占"是现状与设计，clamp 只在客户端 `sanitizeSettings` 做（零迁移优先，不动任何已落盘数据的读写路径）；
**方案 B**：把两键补进宿主白名单，回到"三份清单"。

### 6.10 缓存键与命名：**结论与上一稿相反**

移除提取链后，帧缓存目录里**只剩 `_gpu.png`（实时抓帧）** ⇒ 升 `SCENE_FRAME_KEY_VERSION` 的代价从"所有壁纸重新提取"降为"重抓几张实时帧"（几秒、零画质损失）。
另有第二条理由：若采纳 §6.11 的「抓帧延后到 t≈N」，**抓帧内容本身会变**，旧帧本就该作废。因此建议一并改名并升值：

| 现名 | 目标 | 理由 |
|---|---|---|
| `SCENE_FRAME_KEY_VERSION = 'sf34'` | `LIVE_FRAME_KEY_VERSION = 'lf1'` | 语义已从"静态帧产物"变为"实时帧缓存"，且此时升值很便宜 |

UI 命名：`壁纸画面刷新` → **`出图来源`**（它换的是**来源**，不是"刷新"；`TROUBLESHOOTING.md` 已在使用这一称谓，改名为**归位**）。

### 6.11 开机镜头与预热：把三种「预热」拆开（命运完全不同）

| # | 机制 | 移除静态帧后 | 结论 |
|---|---|---|---|
| ① | **宿主静态帧预提取** `sceneFramePrewarm()`（含 `SCENE_PREWARM_LOGIC` / `prewarm-state.json`） | 服务对象消失；且它 import 的正是将被删的 `extractSceneMainImage*` | **不回归**，随 §6.10 一并删除 |
| ② | **轮换的 live 预载** `prepareSceneLiveStage`（staging 层 `opacity:0` 但满视口几何） | **仍在，而且更重要**（live 是唯一动态来源） | **已经在了** —— 需要的是**延长预热**，不是新建 |
| ③ | **手动切换的 live 启动**（`buildMedia` 直接挂 iframe + 海报，不走准备链） | 同上 | **缺** —— 手动切换必然看到开机镜头 |

**取证结论（决定"跳时间"这条路走不通）**：WebWallGL **不支持渲染特定时刻** —— 渲染页只读 `localAssets` / `resources` / `texcompress` / `texr8`
四个 URL 参数（**无时间参数**），`window.__wp` 的成员表里**没有** `seek` / `setTime` / `renderAt` / `setRuntime`；场景时钟是**内部累积量**
（rAF 里 `performance.now()` 差值累加），外部唯一杠杆是 `pause()` / `resume()`。⇒ 即便上游加了 `setSceneTime(t)`，"跳"也不是纯赋值，
**最便宜的"正确实现"仍是从头快进跑 N 帧 —— 那就是预热。**

**目标：把「首帧就绪」升级为「运行满 N 秒」**（现有就绪判定是 `st.running && st.fps > 0`，首帧一到位就提交，而首帧正是开机镜头）。
**轮换场景下这 N 秒是免费的**（用户正看着上一张），现有机制已覆盖"预热期间用户切走"的各种情况，**不需要新造机制**。
**手动切换（③）两个选择**：**A（彻底）** 也走准备链（牺牲即时反馈）；**B（折中，推荐）** 首次可见保持即时，但**把抓帧延后到 t≈N**（代价接近零，并给 §6.10 的升值多一条理由）。

## 9. 并行轨道 F 的设计要点（字体系统大改）

> **实现位置（收口后）**：`src/font/` 四个文件 —— 三个**纯计算**（角色表 / 令牌 / 钩子生成，不碰 DOM）+ `apply.js`（唯一碰 DOM 的落地点）。
> **通道分工、9 条不变量、扩展步骤、进浏览器包的约束**已全部收口在 [`src/font/README.md`](../src/font/README.md)，**本文不重复**。
> F0 的真机记录（逐条证据、探针代码、两套配色的 377 条令牌取值）保留在 [`F0-THEME-SERVICE-CHECKLIST.md`](./F0-THEME-SERVICE-CHECKLIST.md)。

### 9.1 机制：换成官方令牌层

官方扩展面是客户端 Cordis 服务 **`theme`**，入口是 **`ctx.get("theme")`**，形如 `ctx.get("theme")?.overrideTokens(source, { 令牌: { light, dark } })`。
presenter 把快照写进 **`body` 内联样式** ⇒ 内联胜过主题样式表 ⇒ **不需要 `!important`，也不用 DOM 选择器**（不受类名/结构变化影响，也不碰白闪路径）。
**同 source 再调一次 = 替换该层**（不是追加）⇒ 拖滑杆可实时重算且不累积；卸载随 fiber 移除，无需自己清理。

**F0 真机实测结论（已关闭 · 主路径成立）**：

| # | 结论 | 对方案的影响 |
|---|---|---|
| V1 | 入口**只能是 `ctx.get("theme")`**：`ctx.theme` 裸访问抛错 | **不改 `inject`**（加进去会在服务缺失时 park 整个插件） |
| V2 | `ctx.get` 是**启动竞态**（同实例多次实测 3ms 可用 / 7ms 不可用 → 325ms / 6ms → 418ms） | 必须**延迟 + 轮询**；同步取一次就定论 = 真机静默失效 |
| V3 | 写入**即刻走 `body` 内联** | 免 `!important`、免 DOM 选择器、不碰白闪路径 |
| V4 | `dispose()` **干净还原**（内联摘净，计算值回落样式表） | `fontCustom` 关 = **真·回到原生** |
| V5 | 一层注册**一次**即可**随配色自动换值** | **不要**监听配色变化重注册 |
| V6 | **快照里没有令牌表**（`active.tokens` = 0；`exportInspectTokens()` 仅 14 条），而样式表里 `--dsw-*` / `--dsh-content-*` = **377** 条 | 令牌清单与取值的权威来源是**样式表扫描 + `getComputedStyle`** |
| V7 | 当前 body 上 23 个内联自定义属性里 **0 个 `--dsw-*`** | 「令牌走内联」目前并未发生 ⇒ 我们就是**唯一**往 body 写 `--dsw-*` 的层 |
| V8 | 裸字符串**抛错**；未知令牌**不抛也不生效**；同 source 再调 = **替换** | 必须自己按 **377 条白名单**校验令牌名 —— 写错不报错，只静默无效 |
| V9 | `client-diag` 的 `detail` 两端各截断 **300 字符** | "把令牌清单持续写进 live 诊断日志"需另开通道或只记紧凑摘要 |
| V10 | `--dsw-alias-label-*` 共 **10** 个角色；排版类令牌 **184** 条 | 首期只做颜色是对的；F2 面对的是 184 条排版令牌 |

> 两处**修正**：① 原稿的"实测用量"数字来自蓝图静态扫描，**未在 F0 复测**（F0 只核实了存在性与两套配色值）；
> ② `exportInspectTokens()` 的 14 条 **≠ 可选角色全集** —— 面板"对不存在的角色置灰"不能拿它当依据。

### 9.2 目标模型（4 层）

```
① DSH 主题（内置/第三方）        —— 权威基准，不动
② 我们的字体集（一层 override）  —— 角色令牌表，覆盖在①之上（主体）
③ 作用域覆盖（少量、稳定）       —— 侧栏子树 / markdown / 代码 / 插件自身面板
④ [data-we-font-ignore] 退出契约 —— 第三方子树还原宿主原值（已有，保留）
```

**只存差异**：字体集里没写的角色 = 不覆盖 = 跟随 DSH（旧字体集在新 DSH 上依然可用，也不会把 DSH 未来的改进一起冻住）。
**`fontCustom` 语义不变**：关 = 撤掉我们那一层 + 清空 body 默认层，回到原生。

### 9.3 首期范围（F1）：只做颜色，5 个角色

| UI 名称 | 令牌 |
|---|---|
| 正文 | `--dsw-alias-label-primary` |
| 弱化说明 | `--dsw-alias-label-tertiary` |
| 次要文字 | `--dsw-alias-label-secondary` |
| 极小说明 | `--dsw-alias-label-caption` |
| 禁用 / 更弱 | `--dsw-alias-label-dimmed` ＋ `-primary-dimmed` |

`label-error` **不开放**（错误色有语义）。**"正文字号"不开放** —— 它归 DSH 自己的「通用 → 字号」（`--dsh-content-font-size`）；我们开放的是**阶梯里的其它角色**。

### 9.4 **做不到的部分**（必须写进用户可见文档）

DSH 有大量组件把字号**写死在规则里**（`.sub{font-size:12px}` / `.label{font-size:13px}` / `guideTitle{font-size:20px}` …）。令牌只覆盖"走令牌的那部分"；
想改这些位置只能写**带哈希的组件选择器** —— DSH 一升级即失效，且会扩大失效集。**⇒「任意位置可改」不可行**，这也是"首期不做独立编辑器"的理由。

### 9.5 数据与文件（F3）

| 落点 | 内容 |
|---|---|
| `~/.dsh-wallpaper-engine/fontsets/<id>.json` | 字体集本体（可分享；带 `$schema` 版本，加载时按版本迁移） |
| `~/.dsh-wallpaper-engine/config.json` | **只记** `{ fontSetId, fontCustom }` |

**理由**：localStorage 只有 5MB；宿主白名单漏键会**静默丢弃**（= R4）；滑杆每次回调都同步写 settings 太重。
导入导出复用 `/upload` + 数据目录 + 文件选择器的现有基建（F3 因此依赖 P2-9）。

### 9.6 红线（违反即回归）

1. **白闪红线**：不得引入 `:has()` / 祖先相关选择器；作用域只用属性/类**直接命中**。
2. **令牌层不写 `!important`**；body 默认层维持现状（只在 body 上用）。
3. **不抢** `--dsh-content-font-size`（那是 DSH 自己的字号设置）。
4. **`.we-*` 插件自身面板默认不跟随**（否则用户会把设置面板调糊）。
5. **readability floor 必须保留**：颜色角色化后更容易调出不可读组合 ⇒ 面板对越界值给提示。
6. **令牌名漂移**：未知令牌**静默忽略**；面板对"当前 DSH 不存在的角色"**置灰**。
7. **回落通道**：`theme` 注入失败 ⇒ 回到 `/style` 注入路径（**保留双通道**，按能力探测）。
