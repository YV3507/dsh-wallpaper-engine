## 0. 怎么用这份文档（可跟踪约定）

**状态列取值**：`⬜ 未开工` / `🔄 进行中` / `✅ 已落地（提交号）` / `⏸ 阻塞（原因）` / `➖ 已作废（理由）`。

**「一步三交」（= 边重构边落实设计）**：每一步重构必须**同时**交出三样东西，缺一即不算完成 ——
这条规则就是本文对「边重构边落实设计」的定义，也是 §5 与 §6 的绑定方式：

| # | 交什么 | 判定 |
|---|---|---|
| ① **结构** | 代码的移动 / 删除 / 抽取本身 | 从 `lib/index.js` / `lib/client.js` 出发的**可达闭包干净**：没有悬空 import，没有"删了文件但守卫还引用它" |
| ② **规则** | 该步落地的**不变量**写进代码旁注释（不写编年史、不写日期） | `npm run verify` 里的 `verify-comment-discipline` 不因新增注释而变红；规则只描述"必须/不得"，不描述"曾经" |
| ③ **守卫** | 能机器判定的部分加断言，**正/负对照成对**，并挂进 `npm run verify` | 负对照必须在场（仓库既有做法：断言本身要有牙） |

**执行铁律**（全部来自本项目已付代价的教训，不是通用建议）：

1. **一次提交只切一刀**；一次改动同时做两件事就拆成两次提交。
2. **`npm run verify:all` 未绿不得提交**；若红是**既有/环境性**失败，必须先用 `git stash` 对照证明，
   并在提交信息里写明。
3. **不做批量文本替换**；确需批量时：dry-run 默认、跑飞上限（>80 行即中止）、只改注释行。
4. **删除先行、重写殿后**：本项目 `fix : feat ≈ 1:1`、3 次显式 `Revert`，`TODO.md` 自述"重写前已发生
   ≥5 次修一个坏一个" —— 能用删解决的不重写。
5. **反向探针先于删除**：防复活（沿用 `/scene-anim/` 已用过的做法）。

## 1. 决策（先结论）

**不进行立刻的结构性大重构。先做一轮「减重 + 加固」（零新增功能、风险≈0），再按已验证的接缝分批抽取。**

三条依据：

1. **问题不是"逻辑纠缠"，而是"体量集中 + 边界缺失"。** 代码复制率不足 1%（§3.2），真正的病灶是
   两个文件装了 **46%** 的手写生产代码，而 `src/client.js` 内部**没有任何强制边界**。
2. **大重写会先拆掉唯一的安全网。** 9,533 行守卫目前全绿（实测 `npm run verify` 退出码 0），
   而缺陷率与回滚史说明"一次改对"在本项目并不成立。
3. **当前最高风险不在代码结构，而在工程保障缺口：零 CI。** 唯一 workflow 只管 macOS 分支自动合并，
   9,533 行守卫全靠人记得在本机跑。**这个缺口让"重构"本身变得危险 —— 先补它，再动结构。**

**顺序（详见 §5）**：`P0 加固（零删除风险）` → `P1 单一真源 + 零耦合抽取` → `P2 按接缝抽取` →
`P2 末项 = 静态帧渲染整体移除（§6 的 5 阶段）`。

**并行轨道（功能，非重构）**：`F 字体系统大改（要点见 §9）` —— **F0 真机确认已完成（2026-09-26）**，
结论已并入 §9.1 的 V1–V10；**F1 起必须排在 P1-5 之后**，理由见 §5 的「前置」列（它的数据模型正是建立在
"设置键单一真源"之上）。

## 3. 四组维护难度指标

### 3.1 复杂度：集中在 4 个"巨石"

| 巨石 | 体量 | 近似圈复杂度 | 锚点（符号名优先） |
|---|---|---|---|
| `WallpaperPicker` 组件 | **1,999 行**，最大嵌套 6 | **294** | `src/client.js` `function WallpaperPicker`；55 处直写 store、45+ 内联 handler、8 个内联 render 闭包 |
| `apply(ctx)` 宿主函数 | **2,046 行**（= 插件全部逻辑） | **387** | `lib/index.js` `export function apply(ctx)`；**33 处 `webServer.register` 全在这一个作用域内** |
| 内联 CSS 模板 | **1,833 行** | — | `src/client.js` 的 `CSS` 模板字符串（整站样式表内联在 JS 里） |
| `selection` 全局对象 | **101 个字段** | — | `src/client.js` `const selection`；被 **76 个函数**读写（44 读 / 32 写），而 `DEFAULTS` 只列 60 个 |

补充：`src/client.js` 220+ 顶层函数 / 387 顶层声明；最大花括号嵌套 **7 层**（`startLiveWatch`、
`startMediaSync`、`maybeUpgradeToTranscoded`）；`src/client.js` + `lib/index.js` = 14,797 行 ≈ 手写生产代码的 **46%**。

⚠️ **复杂度的分布比总量更值得注意**：`lib/we-renderer/`（43 文件）是**干净的树**（叶子模块单消费者、
低扇入），`lib/media/` 分层清楚。**烂的是两个门面文件，不是整个仓库** —— 这决定了 §5 的 P2 是"拆门面"
而非"重写内核"。

### 3.2 冗余度：文本不重复，结构重复很重

- **文本级重复极低**：8 行以上重复窗口仅 26 簇、约 8.4k 归一化字符（**<1%**）；**20 行以上 0 簇**。
  ⇒ 不存在"复制粘贴式"的技术债，**不要按"去重复"立项**。
- **结构级冗余**（详见 §4 与 §6.10）：

| 项 | 体量 | 证据 |

| 孤儿路由 + 其专用播放页 | 3 路由 + 1,946 行 | `/scene-runtime`、`/scene-manifest`、`/scene-resource`；`inventory.sceneUrl` 仍被赋值，而 **`src/client.js` 全文零引用 `sceneUrl`** |

### 3.3 耦合度：**一个真接缝 + 一堆全局变量**

**好的一面**：跨端耦合是 **HTTP 协议**，这是干净接缝 —— 宿主 33 处 `register` / 34 条路由 ↔ 客户端
26 处 `fetch` / 19 个端点。**DSH 平台耦合面很小**：`inject = ['webServer']` + 33 处 `register` +
`ctx.loader` 1 处（`ctx.config` / schema / slots / 模型工具**均未使用**）。

**坏的一面**：客户端内部**无接缝** —— 220 个顶层函数里 **124 个（56%）触碰 45 个可变模块级全局**；
唯一的强制边界是 `emit()` 订阅总线，而它是**全局 store 广播**（每个订阅者都拿到整个 store），不是选择性接缝。
跨 React root 的协调也靠全局（`RopeDock` 通过 `repoPanelOwnsModal` + `emit()` 与设置页联动）。

**Git 共变耦合（能量化"改一次要动几处"）**：280 次提交中 **117 次**动 `src/client.js`，其中

| 同改文件 | 次数 | 耦合系数 | 含义 |
|---|---|---|---|
| `lib/client.js`（生成物） | 112 / 117 | 2.37 | **生成物入库** ⇒ 每次都得一起提交 |
| `README.md` | 55 / 117 | 1.69 | 近半数浏览器改动要动门面文档 |
| `lib/index.js` | 53 / 117 | 1.31 | 宿主/客户端协议是主要跨端面 |
| `README.en.md` | 41 / 117 | 1.64 | 中英双份文档 |
| `package.json` | 37 / 117 | 1.48 | 版本 + `files` 白名单 |
| `scripts/verify-client.mjs` | 36 / 117 | 2.33 | 守卫与实现**同改**（镜像校验的必然代价） |

**⇒ 平均每次提交动 7.09 个文件**（49 次提交动了 >6 个文件）。这条指标是 §7 的升级触发器。

## 6. 设计基线：静态帧线移除后的回退形态

> 本节接替原《回退形态设计》草案（已随并入删除，历史见 git）。
> **适用范围：场景类壁纸**；网页壁纸的形态与垫底不在本节范围。
> **设计原则：零迁移优先**（不改用户可感知的持久化语义）／**不新增用户可见开关**／**不留死代码**。

### 6.1 现状：有**两层**，别把两层混成一层

| 层 | 是什么 | 落点 |
|---|---|---|
| **显示链** | 屏上"动态还是静态" | `src/client.js` `function buildMedia` |
| **静帧来源枚举** | 静态时那张图由**哪个来源**产出 | `src/client.js` `FRAME_VARIANTS` |

**显示链**（源码注释称"优先级不变量"）：

```
① live（WebWallGL） → ② sceneVideo（作者内嵌 MP4，poster = 静帧） → ③ 静帧图（sel.url → /scene-frame?v=N）
```

### 6.2 现状：静帧来源档位（本仓库的真实档位）

`FRAME_VARIANTS` ↔ 宿主 `?v=`（有效 `1..4`，缺省/0 → 0）：

| 档 | 客户端标签 | 宿主的真实来源 |
|---|---|---|
| **0** | 合成（分层） | `tryCompositeSceneLayers()` 多层合成；**失败则静默回落到单图排序** |
| **1** | 主纹理（单张大图） | **找最大图片**：遍历包内 `.tex`，按 `面积 × 嵌入格式权重 × 路径惩罚` 打分排序 |
| **2** | 作者原画（嵌入 JPEG/PNG） | **作者 PNG**：包内嵌入 JPEG/PNG 整图按面积置顶 |
| **3** | 预览图 | 直接读工坊目录 `preview.jpg\|png\|gif`（**不经** `pkg-extract`） |
| **4** | 自定义画面 | 用户导入的 `overrides/<id>.*`，缺失 → 422 |

**GPU 实时帧（`<key>_gpu.png`）优先于 v=0–3 的全部档位；v=4 豁免**。该帧由 live 渲染页经
`PUT /scene-frame-cache/<token>` 回填 —— **它是"实时帧缓存"，不是静态帧产物**（此区分决定了它的去留）。

### 6.3 「静态帧渲染」的完整血统 —— 它**不只是**那个离线渲染器

按提交史核实，下面这些**同属一条线，应当一起走**：

| 组成 | 引入 | 说明 |
|---|---|---|
| **找最大图片**（打分排序） | `3666a66` · v0.3.0 | `feat: scene wallpaper static frames with quality gating` —— **这条线的开山提交** |
| **作者 PNG**（嵌入整图置顶） | `3666a66` | 与「找最大图片」同批诞生 |
| 合成（分层） | `3b43034` | 多图层场景按场景变换合成整帧 |
| 档位表把它俩暴露成可切换档 | `152aa74` | 「壁纸画面刷新与自定义画面」 |
| 离线渲染器（`SceneRenderer`） | 更早的静态帧路线 | **在本仓库已无调用点**（§6.5） |

**⇒ 口径确认**：找最大图片与作者 PNG 是"很早期的逻辑"，与渲染器、合成同属「静态帧渲染」。
**⇒ 整条线一起移除**：`extractSceneMainImage*`（**含合成**）、渲染器，以及档位 `1/2/3`。

### 6.4 ⚠️ 一个会从后门活下来的陷阱：`v=0` 的静默回落

```js
// lib/pkg-extract.js（档 0 = 默认档；档 1/2 是"壁纸画面刷新"的备选生成逻辑）
if (!variant) {
  try {

    if (composite) return composite;
  } catch { /* fall through to the single-texture path */ }

```

**只要合成路径还在，删掉 `v=1/v=2` 这两个"档"并不能把「找最大图片」移出自动链。**
本设计因此**连合成一起移除**，从根上断掉这条回落 —— 这也是 §6.12 要求"探针覆盖到
`collectImageObjectTextures` / `FORMAT_PENALTY` 等**实现标识**"的原因：**防它换条路径回来。**

### 6.5 现状取证：离线渲染器**已经是死代码**

- 入口 `lib/index.js` `renderSceneFrameInWorker`（`function renderSceneFrameInWorker`）**只有定义、无调用点**；
  且它**没有被导出**（`lib/index.js` 只导出 `inject` / `apply` / `default`）。
- `/scene-frame` 注释写明原因：提取优先 —— **scene-frame 不再先试 `SceneRenderer` worker**
  （`lib/index.js:3288`）。
- beta 场景动画（多帧/APNG）已移除，`scripts/verify-client.mjs` 有**反向探针**断言其永不复活
  —— P2-12 沿用同一手法。

### 6.6 目标显示链（唯一权威顺序，5 级）

```
① live（WebWallGL 实时渲染）
② sceneVideo（作者内嵌 MP4，/scene-video）        ← 与 ① 同属「动」；作者本意
③ 实时抓帧缓存（场景 _gpu.png / 网页 liveFrame）  ← 「静」的链头；真实画面，不是猜图
④ 自定义画面（用户导入 overrides/）               ← 用户显式资产
⑤ 空（不渲染）                                   ← 全链不可用时的诚实终端
```

- **①→② 顺序不变**：沿用既有优先级不变量 `live > sceneVideo > 静帧` —— 本次只移除静态帧线，
  **不借机改这条已验证的顺序**。
- **③ 是上一稿的缺口，这里补上**：实时抓帧是**这台机器真实渲染出来的**最后一帧，与 ① 同源，
  **优先于 ④**；这与宿主 `gpuFrameFileFor()` 的既有语义（`v=4` 豁免）一致。网页侧的 `liveFrame`
  （`PUT /live-frame/<token>`）现状只用作 live 启动海报；目标形态里它同时是 ③ 的来源。
- **没有 ⑥。明确不做**：不再有任何"替作者猜一张图"的来源 —— 找最大图片 / 作者 PNG / 合成**正是**在干
  这件事，也正是本次要移除的。

### 6.7 目标档位与默认

| id | 名称 | 说明 |
|---|---|---|
| **0** | **自动** | **取链头**（③→④ 中第一个可用者） |
| **4** | 自定义画面 | 沿用既有 id |

**移除 id**：`1`（主纹理/找最大图片）、`2`（作者原画/作者 PNG）、`3`（预览图）。
宿主侧对 `1/2/3` 及越界值一律 **clamp 到 0**。

> 值域里的洞（缺 1/2/3）**有意保留**：它让"哪些档已退役"在数据里可读，同时避免值域迁移。

**默认 = 链头**：`GET /scene-frame/<token>`（**无 `?v=`**）不再隐含"档 0 = 合成"，而是求链头 ——
**有实时抓帧 → 服务它**；否则有自定义画面 → 服务它；否则 → 404 / 空态（客户端走 ⑤）。
`?v=4` 仍是"强制自定义画面"（缺失 → 422，客户端明示"自定义画面已失效"）。

### 6.8 失败语义与终端

| 环节 | 目标行为 |
|---|---|
| live 首帧逾时 / 运行期失联 | 记 `sceneLiveFailures[id]` → 前进到 ②；**同会话对该壁纸不再重试 live**（现状即此，保留） |
| ② 内嵌 MP4 | 取不到 → 静默前进；**不记失败记忆**（作者没给视频是常态，不是故障） |
| ③ 实时抓帧 | 缺失 → 前进到 ④ |
| ④ 自定义画面 | 缺失 → 前进到 ⑤ |
| ⑤ 空 | **留空**，状态行给出可判定原因。**不回落任何"猜图"来源**，也不回落预览图 |

### 6.9 零迁移论证（含一处**与现状冲突**的点，需拍板）

- 用户可感知的语义不变：**"我为这张壁纸 pin 过一个来源"这个事实仍被记住**。被移除的 pin 值
  （`1/2/3`）**clamp 到 0（自动）** ⇒ 旧配置**原样可用**，只是那条 pin 变成"自动"。这是唯一可接受的
  降级方向 —— 反向（把 auto 变成某个具体档）会让老配置被误读成用户没选过的来源。
- `customFrames`（`{[id]: true}`）形状不变；`sceneLiveFailures` 值域不变。
- ⚠️ **冲突点**：本设计原稿要求"三个键必须同时存在于**客户端发送 / 宿主白名单 / 客户端读回**三份清单"，
  但现状是 `frameVariants` 与 `customFrames` **被显式钉为客户端独占**（`scripts/verify-client.mjs`
  的 `CLIENT_ONLY`），宿主白名单里没有它们。二者必须二选一并在同一提交里把**注释、守卫、文档**一起改：
  - **方案 A（推荐）**：承认"客户端独占"是**现状与设计**，clamp 只在客户端 `sanitizeSettings` 做；
    把不变量改写成"这三个键**明确为客户端独占**，宿主不得白名单"。
  - **方案 B**：把两键补进宿主白名单，回到"三份清单"。
  选 A 的理由：**零迁移优先** —— 改 A 不动任何已落盘数据的读写路径。

### 6.10 缓存键与命名：**结论与上一稿相反**

移除提取链后，帧缓存目录里**只剩 `_gpu.png`（实时抓帧）** —— 提取产物 `<key>.png|jpg|gif` 不再产生，
自定义画面存在 `overrides/` 而不进缓存目录。

**⇒ 升 `SCENE_FRAME_KEY_VERSION` 的代价，从"所有壁纸重新提取"降为"重抓几张实时帧"（几秒、零画质损失）。**
另有第二条理由：若采纳 §6.11 的「抓帧延后到 t≈N」，**抓帧内容本身会变**，旧帧本就该作废。
因此本稿**建议一并改名并升值**：

| 现名 | 目标 | 理由 |
|---|---|---|
| `SCENE_FRAME_KEY_VERSION = 'sf34'` | `LIVE_FRAME_KEY_VERSION = 'lf1'` | 语义已从"静态帧产物"变为"实时帧缓存"，且此时升值很便宜 |

UI 命名：`壁纸画面刷新` → **`出图来源`**（它换的是**来源**，不是"刷新"；"刷新"会被误读成重抓实时帧
—— 那是「实时帧」行的「重新截」）。`docs/TROUBLESHOOTING.md` 已在使用「出图来源」这一称谓，改名为**归位**。

### 6.11 开机镜头与预热：把三种「预热」拆开（命运完全不同）

| # | 机制 | 它解决什么 | 移除静态帧后 | 结论 |
|---|---|---|---|---|
| ① | **宿主静态帧预提取** `sceneFramePrewarm()`（含 `SCENE_PREWARM_LOGIC` / `prewarm-state.json` 记账与开机自调） | 把 CPU 提取等待移出交互路径 | **服务对象消失**；且它 `import` 的正是将被删的 `extractSceneMainImage*` | **不回归**，随 §6.10 一并删除 |
| ② | **轮换的 live 预载** `prepareSceneLiveStage`（staging 层 `opacity:0` 但满视口几何 → 渲染页全分辨率初始化 → 首帧就绪后节点级领养） | live 冷启动窗口（拉 pkg + 纹理上传） | **仍在，而且更重要**（live 是唯一动态来源） | **已经在了** —— 需要的是**延长预热**，不是新建 |
| ③ | **手动切换的 live 启动**（`buildMedia` 直接挂 iframe + 主题色海报，不走准备链） | 同上 | 同上 | **缺** —— 手动切换必然看到开机镜头 |

**取证结论（决定"跳时间"这条路走不通）**：WebWallGL **不支持渲染特定时刻** —— 渲染页只读
`localAssets` / `resources` / `texcompress` / `texr8` 四个 URL 参数（**无时间参数**），`window.__wp`
的成员表里**没有 `seek` / `setTime` / `renderAt` / `setRuntime`**；源码里的 `seek`/`setTime` 命中全在
**视频纹理**与通用媒体控制上，不是场景时钟。场景时钟是**内部累积量**（rAF 里 `performance.now()`
差值累加），外部唯一杠杆是 `pause()` / `resume()`。
**⇒ 即便上游加了 `setSceneTime(t)`，"跳"也不是纯赋值**（动画控制器/粒子/脚本状态都是累积的），
**最便宜的"正确实现"仍是从头快进跑 N 帧 —— 那就是预热。**

**目标：把「首帧就绪」升级为「运行满 N 秒」。** 现在 `prepareSceneLiveStage` 的就绪判定是
`st.running && st.fps > 0`（`src/client.js:1677`）—— **首帧一到位就提交，而首帧正是开机镜头**。改成"首帧就绪**且**已运行
≥ N 秒"即可跨过去。**轮换场景下这 N 秒是免费的**（用户正看着上一张）；现有机制已覆盖"预热期间用户
切走"的各种情况（`PREPARE_LIVE_TIMEOUT_LIMIT`、隐藏期保持上限、隐藏期轮询），**不需要新造机制**。

**手动切换（③）两个选择**：
- **A（彻底）**：手动路径也走准备链 —— 代价是牺牲"即时反馈"。
- **B（折中，推荐）**：手动切换的**首次可见**保持即时（接受开机镜头），但**把抓帧延后到 t≈N** ——
  于是"降级时 / 切走再切回时看到的静帧"是干净的。代价接近零，并给 §6.10 的升值多一条理由。

### 9.1 机制：换成官方令牌层

- 官方扩展面是客户端 Cordis 服务 **`theme`**，入口是 **`ctx.get("theme")`**（**不是** `ctx.theme` —— 见 V1），
  形如 `ctx.get("theme")?.overrideTokens(source, { 令牌: { light, dark } })`。
- **怎么生效**：presenter 把快照里的令牌**写进 `body` 内联样式** ⇒ **内联胜过主题样式表**，因此令牌层
  **不需要 `!important`，也不用 DOM 选择器** ⇒ 不受 DSH 类名/结构变化影响，也**不碰白闪路径**。
- **卸载**：该层随 fiber 一起移除，presenter 重新组合并摘掉变量（不需要我们写清理）。
- **同 source 再调一次 = 替换该层**（不是追加）⇒ 拖滑杆可实时重算，且不会累积。
- **浅/深强制成对**：传裸字符串会**抛错**（API 的报错原文理由是"单值在用户切换配色后必然不可读"）
  ⇒ 我们的 schema 也跟着强制两套；排版令牌写两侧同值。

**F0 真机实测结论（2026-09-26 已关闭 · 主路径成立）** —— 实装 `D:\DSH Desktop\resources\app`
（DSH 0.1.7-rc.1 / cordis 4.0.4）。逐条证据、探针代码与原始数据见
[F0 清单](./F0-THEME-SERVICE-CHECKLIST.md)（§C3 实测表 / §C4 结论）：

| # | 结论 | 对方案的影响 |
|---|---|---|
| V1 | **入口只能是 `ctx.get("theme")`**：`ctx.theme` 裸访问**抛错** `cannot get property "theme" without inject` | **不改 `inject`**（加进去反而会在服务缺失时 park 整个插件）；访问一律 `ctx.get` + `try/catch` |
| V2 | **`ctx.get` 是启动竞态**：同一实例多次实测为 `3ms 可用` / `7ms 不可用 → 325ms 可用` / `6ms 不可用 → 418ms 可用` | F1 必须**延迟 + 轮询**（如 250ms × N）或等服务就绪事件；拿到前保持今天的 `/style` 路径。**同步取一次就定论 = 真机静默失效** |
| V3 | 写入**即刻走 `body` 内联**（内联与计算值同刻改变） | 免 `!important`、免 DOM 选择器、不碰白闪路径（原论证成立） |
| V4 | `dispose()` **干净还原**：内联被摘净（`after=""`），计算值回落样式表（`afterComputed=#f9fafb`） | `fontCustom` 关 = **真·回到原生**，可放心依赖 disposer |
| V5 | 一层注册**一次**即可**随配色自动换值**（`{light,dark}` 由快照按 `active.colorScheme` 合成） | **不要**监听配色变化重注册 |
| V6 | **快照里没有令牌表**：`getTheme().active.tokens` = **0**（`themes` = `light:light:0 dark:dark:0`）；`exportInspectTokens()` = **14** 条（只是"设置目录"）；而样式表里 `--dsw-*`/`--dsh-content-*` = **377** 条 | 令牌**清单与取值的权威来源是样式表扫描 + `getComputedStyle`**（即 F0 §C1 那套）；**不能**用 `active.tokens` 或 `exportInspectTokens()` 当全集 |
| V7 | 当前 body 上 23 个内联自定义属性 = `--dsh-content-font-size` + 22 个本插件 `--we-*`，**其中 0 个 `--dsw-*`** | 「令牌走内联」目前**并未发生**（没令牌可写）⇒ 我们就是**唯一**往 body 写 `--dsw-*` 的层；"现状内联数 > 0"不能当成令牌机制的证据 |
| V8 | 语义边界：裸字符串**抛错**；未知令牌**不抛**但也**不生效**；同 source 再调 = **替换**（`#111111→#333333`） | F1 必须自己按 **377 条白名单**校验令牌名 —— 写错不会报错，只会**静默无效** |
| V9 | `client-diag` 的 `detail` 两端各截断 **300 字符**（本次实测印证：完整对象只能靠控制台取回） | "把令牌清单持续写进 live 诊断日志"**需另开通道或只记紧凑摘要** |

### 9.2 目标模型（4 层）

```
① DSH 主题（内置/第三方）        —— 权威基准，不动
② 我们的字体集（一层 override）  —— 角色令牌表，覆盖在①之上（主体）
③ 作用域覆盖（少量、稳定）       —— 侧栏子树 / markdown / 代码 / 插件自身面板
④ [data-we-font-ignore] 退出契约 —— 第三方子树还原宿主原值（已有，保留）
```

**只存差异**：字体集里没写的角色 = 不覆盖 = 跟随 DSH。这样旧字体集在新 DSH 上依然可用，也不会把
DSH 未来的改进一起冻住。**`fontCustom` 语义不变**：关 = 撤掉我们那一层 + 清空 body 默认层，回到原生。

> 今天把 `primary` / `secondary` / `tertiary` / `dimmed` **四个角色压成同一个用户色** —— 这正是
> "全局同字色不如原生"的根因：它把 DSH 的四级文字层次**压平**了。**分角色上色是收益最大、风险最小的一步。**

| 正文 | `--dsw-alias-label-primary` | 353 |
| 弱化说明 | `--dsw-alias-label-tertiary` | 329 |
| 次要文字 | `--dsw-alias-label-secondary` | 270 |
| 极小说明 | `--dsw-alias-label-caption` | 91 |
| 禁用 / 更弱 | `--dsw-alias-label-dimmed` ＋ `-primary-dimmed` | 14 |

`label-error` **不建议开放**（错误色有语义）。**"正文字号"不开放** —— 它归 DSH 自己的「通用 → 字号」

### 9.4 **做不到的部分**（必须写进用户可见文档）

DSH 有大量组件把字号**写死在规则里**（实测 `.sub{font-size:12px}`、`.label{font-size:13px}`、
`guideTitle{font-size:20px}` …）。令牌只覆盖"走令牌的那部分"；想改这些位置只能写**带哈希的组件选择器**
（如 `.bRiYeG_guideTitle`）—— **DSH 一升级即失效**，且会扩大失效集。
**⇒「任意位置可改」不可行**：这是本方案与 napcat-webui 那类注入方案的分界，也是"首期不做独立编辑器"的理由。

| 落点 | 内容 |
|---|---|
| `~/.dsh-wallpaper-engine/fontsets/<id>.json` | 字体集本体（可分享；带 `$schema` 版本，加载时按版本迁移） |
| `~/.dsh-wallpaper-engine/config.json` | **只记** `{ fontSetId, fontCustom }` |

**理由**：localStorage 只有 5MB；宿主白名单漏键会**静默丢弃**（= R4）；滑杆每次回调都同步写 settings 太重。
**导入导出**复用 `/upload` + 数据目录 + 文件选择器的现有基建（F3 因此依赖 P2-9）。

### 9.6 红线（违反即回归）

1. **白闪红线（v0.6.4）**：不得引入 `:has()` / 祖先相关选择器；作用域只用属性/类**直接命中**。
2. **令牌层不写 `!important`**；body 默认层维持现状（只在 body 上用）。
3. **不抢** `--dsh-content-font-size`（那是 DSH 自己的字号设置）—— 面板上给一句指引，避免用户以为两处冲突。
4. **`.we-*` 插件自身面板默认不跟随**（否则用户会把设置面板调糊）。
5. **readability floor 必须保留**：颜色角色化后更容易调出不可读组合 ⇒ 面板对越界值给提示。
6. **令牌名漂移**：未知令牌**静默忽略**；面板对"当前 DSH 不存在的角色"**置灰**（配合 F0 的探针）。
7. **回落通道**：`theme` 注入失败 ⇒ 回到今天的 `/style` 注入路径（**保留双通道**，按能力探测）。

### 9.7 待拍板（4 条，来自原稿）

1. 首期只做颜色（推荐），还是颜色 + 字号一起上？
2. 颜色默认**单色**（内部自动派生浅/深两套）还是**强制两套**？
   （推荐：默认给一个色 + 「深色单独设置」开关，降低心智负担，但内部始终存两套。）
3. 字体集要不要带 `author` / 分享字段（决定是否朝社区分享做）？
4. 独立编辑器面板：等角色表稳定，还是首期就做？
